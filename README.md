# ra2-commander

**让 Claude 的多个 AI Agent 实时指挥网页版红色警戒2，在 [gonghui.k0s.cn](https://gonghui.k0s.cn/)（《王二火大 / Chrono Divide》）上和电脑 AI 打遭遇战，并且每打一局就复盘、学习对手、进化出下一代打法。**

> A [Claude Code](https://claude.com/claude-code) skill that lets multiple AI agents command a Red Alert 2 web remake (Chrono Divide / 王二火大 at gonghui.k0s.cn) in real time against the built-in AI, then review each match, learn the opponent's tactics, and evolve the next generation of strategy.

---

## 它能做什么

- **接管游戏**：在页面里注入一个 250ms 的执行层，自动完成展开基地车、建造、生产、放置建筑、部队集结、迎击、修理、进攻和拆家。
- **多 Agent 实时指挥**（至少 2 个 subagent 同时在线）：
  - **指挥官**：读战场情报，调整姿态（守/攻/骚扰）、兵种比例、防御、出击时机。
  - **情报分析员**：盯对手的建造、兵力、行军路线，对照对手档案，提前发预警。
  - **后勤官**（可选第三个）：负责经济和生产节奏。
- **赛后学习**：复盘学习员导出全局数据，生成双方时间线，更新**对手档案**和**战术库**（每条战术带证据和置信度）。
- **进化**：基于证据生成下一代方案（带版本谱系和战绩）。下一局自动使用最新方案；新方案连续输棋时回退。

**match-007（v006 首战，v006 → v007）**：又是盟军对手，但玩法是第三种——早期步兵伏击 + 后期 JUMPJET 空降长驻拆家。用户看完战报直接追问"依然给坐下的步兵摧毁大部分"，逼出了这局最关键的一次代码审计：match-006 加的静止步兵伤害加权（`threatValue` 按 1.6 倍算）只喂给了日志展示和"进攻部队要不要回防"两处，**防守分支本身从头到尾没有任何撤退判断**，3 辆灰熊 + 5 个步兵原地被磨到 0 也不会主动撤——这不是权重数值选小了，是压根没接上决策链路。现场用 `game.rules.getWarhead().proneDamage` 还核实到一个新机制：卧倒步兵当被攻击目标时会额外减伤（AP 武器只有平时一半的伤害），综合下来真实劣势约是表面数字的 3.3 倍。用户还追问了一个更根本的问题——"整个指挥战斗能力不行，是 LLM 不够快还是方案有问题"，逼着做了一次系统性复盘：执行层里有几条自动规则（比如"10 秒没看到敌人、单位数够了就出击"）会在任何 LLM 反应之前就把资源花出去，这是设计问题不是速度问题；LLM 的战略判断记录下来几乎全是对的，但从"看到问题"到"改完方案生效"往往要 1-2 分钟，这个窗口期的损失只能靠给执行层加更多自动预警去缓解，不能靠让 LLM 想得更快解决；v005 把 `vehicleMix.aaVehicle` 整个拿掉是对"古巴/苏军通常没有空军"的过拟合，现在两局盟军对手都带 JUMPJET，这个决定被验证是错的。执行层这次改了五处：给防守交战补上退出条件（`defendRetreatRatio`，跌破比例就撤回基地不再硬拼）、敌机实际逗留基地附近时防空建筑绕开资金门槛、攻城自动出击要求至少含 1 个载具（避免纯步兵冲锋）、持续交战每 10 秒刷新一次日志避免低估交战规模。方案层 v007 改 3 个字段：`defenses.aaDef` 缺省→1（防空写进初始方案，不用等触发）、`siegeAutoAttackUnits` 8→14（吸收本局指挥官临场验证过的修正）、`vehicleMix.aaVehicle` 恢复为 1。

**match-008（v007 首战，v007 → v008）**：match-007 那批修复的第一次实战检验，结果好坏参半，如实记录。`defendRetreatRatio` 生效了一次（2:48，在打出有利交换后主动收手，避免过度消耗），但第二次交战里两辆载具在同一次采样窗口一起阵亡，比例从 61.5% 直接跳到 0%，中间没有任何一次采样落在 40% 阈值上——这不是数值选小了，是"按比例判断"这个方法本身在残部基数很小时存在结构性盲区。补了一个绝对值下限（`defendMinValue`，跌破这个绝对值也撤，不管比例）作为部分缓解，但如实说明这只覆盖"基数已经很小"的场景，两个单位一起阵亡导致价值直接跨过绝对值门槛的极端情况仍然覆盖不到，真正彻底的修复需要在每次伤亡事件后立刻重新评估，而不是等固定周期的下一次采样，这次没有做这么大的架构改动。指挥官本局第一次真正执行 T-020（确认古巴阵营后收紧步兵、转投坦克+光棱塔），首波交换比从上次的 1:1 打平提升到我方略优；但也暴露了新问题——光棱塔造价 1500，2:33 排产到判负都没能真正参战，指挥官现场提出一个具体建议：既然 match-007 已经给防空建筑做过"敌机逼近时绕开资金门槛"的例外，光棱塔这类反装甲塔也该有等价的例外。这条建议直接采纳并实现：敌方重型载具/高价值步兵逼近时，`strongDef` 只要资金够造价 30% 就能排产。GHOST2 的一发 C4 在 3 秒内拆了 3 座矿厂 + 1 座碉堡，是第二次独立证实"70% 血量才触发修理"这套逻辑对一击必杀完全无解——这个问题依然没有解决，需要更多局数据支撑再决定怎么改。方案层 v008 只改 1 个字段：`defenses.baseDef` 2→3。

**match-009（v007 第 2 局，赢棋，v007 → v008 → v009）**：本系列第 2 胜，也是第一次以苏军身份取胜、第一次战胜苏军 AI。这局最值得记的不是赢，而是**赢的方式暴露了一个结构性缺陷**：执行层的自动转攻规则要求"连续 10 秒看不到敌方部队"，而它统计的是全地图可见单位。这个引擎没有战争迷雾、探过的区域永久可见，所以只要侦察过一次敌基地，对方缩在家里的 15 个单位就永远算"看得到"，那条规则**对龟缩型对手永远不会触发**。本局我方 25 个单位对敌方 15 个、`attackMinUnits` 早已满足，规则一次没响，最后是指挥官 5:19 手动改 `stance` 才打出去——**一个必须靠人兜底才能赢的自动化系统，等于没有自动化**。修法不是调阈值（怎么调都没用），而是换判据：只统计"野战部队"（离敌方出生点 >15 格），这正是 `intel` 里 `field` 已经在用的口径，也是 T-024 原本想表达的意思。但只换判据会比原 bug 更糟——兵力和龟缩敌人持平时也会触发一次 74 格远征——所以加上了 T-005 的硬条件（我方价值 ≥ 敌方 2 倍），并让它只差这一条时打一条 warn，让实时角色看得见反射卡在哪一步，而不是像本局的 analyst 那样只能从 `status.attack=null` 反推。

这局还查出三处必须靠对局数据才能发现的问题：**① 核电站**——7:25 拆掉 `NANRCT` 与 `[loss] HTNK:3` 在同一时间戳，一次损失 2700，是整局单次最大战损；原因是核电站 `rules.power > 0`，被 `siegeRank()` 归进 rank 1（仅次于建造厂），等于我们主动把坦克堆在一颗炸弹上当作第二优先目标。改成排最后，没有代价——能打到它时敌方已经没气了。**② 矿车护卫**——`minerEscort` 的实现是把护卫摆在**矿厂建筑**旁，而 T-026 提案要求的是待在**矿区矿格**；矿车是在基地外挖矿的，站在矿厂旁边拦不住任何去野矿打矿车的人，本局开了这个字段、零可观测效果。**③ 战果统计口径**——`intel` 只给滚动的事件窗口，不给累计口径，结果两个实时角色**各自独立**算错了同一场交战的交换比（报 2.8:1，实为 1.76:1，高估 59%），而指挥官的转攻决策引用的正是这个错数字。补了 `tally` 累计段。复盘还纠正了两处叙述错误：TESLA 是 v004 起就在初始 plan 里的、不是 v007 的功劳；"交换比从 1.13 提到 2.8"也不成立——1.13 是 match-004 的整局口径、2.8 是单场口径，同口径重算 match-004 是 1.39/1.17/2.42，1.76 落在中间。T-017 的价值由"基地不被拆 + 把它科技节奏推后 1–2 分钟"支撑，不由交换比支撑。方案层 v009 只改 1 个字段：`vehicleMix` 删掉 `aaVehicle`（对陆战型对手约 20% 载具产能会变成 500 块的防空车，本局那 3.56 倍兵力差就是这么堆出来的；注意是**省略键**而非写 0，否则会关掉 `airSeen` 反射）。

**match-010（v009 首战，v009 → 未 promote，维持 v009）**：前段打得很漂亮——3:02 敌方一次性甩出 6 架 JUMPJET 打首波空降速攻，指挥官及时把 `aaDef` 从 1 提到 2，累计歼灭 14 架 JUMPJET，交换比一度 2.1:1，是本系列最佳空防战绩。但 5:48 敌方甩出 MGTK+SREF——这是 match-006 记录的"经济碾压变体"的招牌单位，此前以为和"空降速攻"是两种互斥打法，这局证明**同一个对手会先后打出来**（先空袭削弱、再地面复合波推平），而且比档案早了近 1 分半，叠加还没清完的空袭残部把防守打穿，6:37 建造厂失守。用户中途发现矿车集体停在原地不动，现场排查揪出一个存在了至少 5 局的静默 bug：`army()` 里矿车被打后 `Move` 回基地保命的反射，从来没有再派它们出去挖矿——这个引擎里矿车收到显式 Move 指令后不会自动恢复采矿，指令队列清空就永久闲置；主会话在场时手动把矿车重新派回矿区，25 秒后确认矿量恢复。学习员回查确认这条反射在 match-005/007/008/009 至少还触发过 7 次，每次触发后"矿车总数"曲线都表现出同一种"再不增长"的模式，全部没被抓到——是本系列迄今影响面最广的一次经济漏失。执行层修了两处：矿车血量恢复且周边安全（或等够 40 秒）就自动重新派回最近的矿格；`defendMinValue` 加了"这场交战确实掉过血"的前提条件（之前开局阶段部队总值天然偏小时，即使正在打赢也会被误判成"撤退"）。两个直接败因（一个是执行层 bug、一个是单样本对手变体、其第一阶段应对已经证明有效）都没有足够证据支撑 plan 字段调整，学习员判断维持 v009 不变，没有 promote 新版本。

**match-011（v009 第 2 局，赢棋，v009 → v010）**：本系列第 3 胜，也是第一次打赢盟军的"复合速攻"，第一次以苏军身份打赢盟军。最有说服力的一点是**这是一次干净的对照**：阵营、出生点、连开局到首波的秒表都与 match-010 逐条重合（0:46 军犬、1:00 步兵、1:41 JUMPJET 建成、2:59 首见 6 架混编首波），唯一的实质差别是防空落地时间——本局 2:14 决策、2:29 落地第二座 NAFLAK，比首波早 30 秒；match-010 同一决策拖到 3:53。同样的对手、同样的剧本，结果由负转胜。

攻城阶段则暴露了 match-009 那次修复的一个盲区。match-009 修好了"什么时候该转攻"，但没管"转攻之后被挡住怎么办"：`siege()` 遇到攻城集团附近的敌军时，只是把拆建筑的目标清掉、把目标让给部队，却不下任何攻击指令——它假设 `army()` 的迎击逻辑会接手，可进攻状态下 `AttackMove` 早已到达终点、单位处于空闲，于是**一整支 16 单位的攻城集团在一辆停在 9 格外的 56% 血防空车对面空转了 2 分 51 秒**，还顺手损了 4 辆犀牛、让敌方补起 2 座碉堡。修复是给这个分支补上主动攻击：当挡路的敌军总价值不到我方集团 25% 时，全组直接攻击最近的那个。归因也做了严格裁定——指挥官 8:35 改 `attackTarget` 与这次停滞无关（`near` 判定跟目标无关、分队 8:32 就已在原地），真正的恢复是那辆防空车自己死掉；分析员"显式目标能直接解除停滞"的假设不成立。这条修复（`rt-579f6a23dc`）是当场热补丁进对局的，本轮才连同 rest 一起提交。

方案层 v010 改 2 个字段：`defenses.aaDef` 1→2、`targetRefineries` 4→3。前者是把"发现盟军再补防空"改成**预置**——盟军 2/2 局都需要第二座 NAFLAK，预置后它在雷达前的 Armory 空窗排产，不再和 2:24 后的 TESLA 抢资金（本局 TESLA#1 因此拖到 3:27）；非盟军局由指挥官在确认阵营的同一轮降回 1，**默认高、发现后降，比默认低、发现后追可靠**。后者是因为第 4 座矿厂由对账补建、没有资金门槛，本局两次错时排产（4:10 资金 101、7:21 资金 640）各自触发资金饥饿反射，4:42 取消时已造到 75%，最终 8:51 才落地、对结果零贡献——交给指挥官在"野战部队为 0 且资金充足且不在攻城收尾"时手动加。明确不改的：`strongDef` 维持 1（第二座从未被检验）、`siegeAutoAttackUnits` 维持 14（本局恰好避开第三波，改成 12 会在 5:12 把部队送出门）。战术库新增 T-034（转攻同轮把 `infantryCap` 归零，攻城期步兵增援只会单兵穿过碉堡群送死）、T-035（`siege()` 的"附近有敌军就暂停"必须配主动攻击）、T-036（转攻路线顺手杀矿车封死对手的第二种雪球，支持 2）。

**match-012（v010 首战，赢棋，v010 → v011）**：本系列第 4 胜，也是第一次在对手也造出 MGTK/SREF 的情况下取胜。这局前半段打得干净：v010 预置的 `aaDef:2` 让第二座 NAFLAK 在 1:25 就落地，首波 6 架 JUMPJET 混编 30 秒全歼；指挥官 3:48 提前执行 T-034 把 `infantryCap` 归零，第二波 7 架零损吃下，tally 一度 4.6:1。

但整体用了 **23 分 31 秒，是系列最长的一局**，而且慢的原因几乎全在自己身上。拆掉建造厂（13:12）之后的 619 秒里**只有 223 秒在交战，396 秒（64%）是行军和干等**；两段"撤退 → 再集结"的空档就占了 7 分 30 秒，而**那期间我方交换比是 4.71:1、敌方 field 为 0**。四次转攻的交换比 0.90 / 0.32 / 0.96 / 0.98：前三次都正面撞上南侧碉堡群（分析员三次建议从西北侧矿厂绕开，只在最后被采纳），第四次改成"不等齐兵力、持续压迫 + 增援流"后 **49 秒就打到 field 归零**。三处执行层修正：**目标顺序按"离结束比赛有多近"排**（全视野实测锁定判负只看生产建筑组合——23:26 它还有兵营+3 矿厂+维修厂时没判负，23:30 最后一座兵营倒下立刻判负，所以生产建筑提到建造厂之后，此前先拆电厂和碉堡白花了 30 秒）；**轻微骚扰不再打断拆迁**（15% 以下直接无视，此前一个价值 180 的动员兵把 8–11 个单位从建筑上拽走 6 次，是三次收不了尾的直接原因）；**清场模式**（敌方野战力量 < 1500 时全军压上、撤退下限压到 0.14、阻挡容忍度放宽到 60%）。

这局还揪出一个**双方通病**的引擎级 bug：任何显式指令（包括 `Move`）都会永久取消矿车 AI，于是"被打 → Move 回基地保命 → 再也挖不了矿"。match-010 的"修复"用 `Move` 把矿车重新派回矿区——**拿病因当药**，车到了矿区仍然零指令零任务。本局我方 6 辆 HARV 与**敌方 3 辆 CMIN 同时冻结、双方资金一起归零**，这才是 23 分钟的机制解释（不是它强，是双方都被同一个 bug 卡住）。正解是调用引擎原生的 `harvesterTrait.queueAutoGatherAfterOwnershipSettles(unit, game)` 重新武装，靠读引擎源码拿到签名并当场实测（`ore 0→3`、`tasks 0→1`），实测后资金 20:24 转正。方案层 v011 改 2 个字段：`retreatRatio` 0.35→0.14、`siegeAutoAttackUnits` 14→10（本局 11:23 有 11 个战斗单位 /8300 对敌方 3600、早已满足 2 倍门槛，却卡在 14 的单位门槛上，最后靠指挥官手动转攻——与 match-009 同因）。

**match-013（v011 首战，输棋，v011 → v012）**：v011 两处改动的第一次实战，结果是**两处都被数据推翻、v012 全部回退**。这一局的价值不在于输赢，而在于它同时否证了上一局的结论、又暴露了上一局修复自带的两个 bug。

**决策层**：前 4 分钟塔线打出 4.67:1 后，指挥官在 4.67:1 优势下转攻，但它把"敌方野战部队为 0"读成了"敌基地是空的"——转攻前 `knownBuildings` 里连一座 `CAPILL` 都没有，15 单位/9540 直接撞进 4 座古巴重碉堡（650 元 / HP 600，比苏军防空塔硬）。68 秒后剩 5 单位/2610，对三类生产建筑零击破，唯一战果是雷达和一座 `CAPOWR`——**两座都不在判负集合里**（雷达被拆后 5:02 重建，碉堡从 2 座补到 4 座）。指挥官自己的结论：`T-005` 的 2 倍门槛只保证"出门不被野战部队吃掉"，不保证"能拆得动家"。

**执行层**——这一局修出三处，两处是上一局修复自带的：
- **撤退判据口径不一致（T-039）**：分子数的是"当前编组里的活单位"，分母却是"发起时的编队"。本局 4:12 那 15 个单位到 5:00 已 100% 阵亡，5:06 读到的却是 2610（27%，将近下限的两倍）——**因为那全是三辆替补新坦克**，于是自动撤退一次都没触发。已改为只数发起时那批单位（`launchIds`）。这也解释了同一个固定比例为什么在 match-012 显得太早、在这里又永不触发：**是同一个指标的两面**。0.35 目前只是临时值。
- **清场模式忽略静态防御**：本局敌方 `field=0` 但有 4 座重碉堡，清场模式照样激活。已加条件：`field<1500` **且** 无防御建筑。
- **清场模式绕过集结点**：上一局为"全军压上"加的 `finishing ||` 让新出厂坦克不集结、一辆辆单走 70 格去撞碉堡群——**22 辆 MTNK 全灭**。已撤销（这是 match-012"打得好却撤退"的镜像错误）。
- **反击反射攻城期限兵**：用户要求的"谁打我们就打谁，建筑也算"本局是最成功的机制（13–18 次触发，每次 1–5 秒内必跟击杀），但攻城窗口内 **7 次共 17 个单位次**被从建造厂拽走去打非判负建筑，最严重一次用 7 个单位打一座 `CAPOWR`，那 68 秒里 **54% 的时间不在目标上**。已限制为攻城期最多 3 个单位回击，防守自家基地不限。

**判负判据**：本局把它从 1 局样本推到 2 局、且正反两侧都验证。判负只看**建造厂 + 兵营 + 战车工厂 + 空指部/雷达这 4 类能造出单位的建筑**：match-012 里 `GAAIRC` 23:20 倒、`GATECH` 23:24 倒都没判负，`GAPILE` 23:30 倒才立刻 `over`；本局我方 6:16 丢建造厂、7:58 丢战车工厂都没判负，8:00 兵营+空指部同 tick 倒下 → 8:01 立刻判负。**作战实验室（`GATECH`）不计**——上一版把它和 4 类并列是错的，拆它浪费拆迁时间。诚实保留：本局判负那一刻我方建筑总数为 0，"生产建筑全灭"与"建筑全拆光"同时满足，严格讲只证明了这 4 类是**必要条件**。

方案层 v012 把 v011 的两处改动全部回退：`retreatRatio` 0.14→0.35、`siegeAutoAttackUnits` 10→14。

**match-014（v012 首战，输棋，v012 → v013）**：这一局的价值在于**它验证了上一局的教训真的被吸收**——`knownBuildings` 整局为空（3 只侦察犬全灭），指挥官因此**全局一次进攻都没发起**，没有重演 match-013 的盲撞。分析员三次给出"转攻前置条件"，其中一句是整局的关键判断：**"它家 `atEnemyHome` 读 0 纯粹是因为我们一点视野都没有，那是'看不见'不是'没有'"**。

但代价是：**v012 的 4 个进攻侧修复本局一个都没被检验**（清场模式、`launchIds` 撤退判据、轻微骚扰忽略、反击攻城限兵全部 0 次触发）。复盘里如实标注为"未验证"，没有当成有效。

真正的死因是**防御侧的两个长期 bug**，两个都由本局暴露并修复：

- **防御排产的 `break` 写错了位置**：循环里 `break` 原本在 `if` 外面，只评估**第一个**不满足的角色就退出；配上按 `baseDef→aaDef→strongDef` 的对象键序，**一个买不起的 baseDef 会永久否决后面所有防御**。指挥官 7:40 把 `baseDef 3→4` 与 `strongDef 1→2` 写进同一批，而 baseDef 资金长期为 0 永远满足不了，于是 `strongDef` **86 秒内 0 次被求值**——唯一能打 MGTK/SREF 的第二座 ATESLA 连排产都没进。按资金账回放：若初始方案就写 `strongDef:2`，它会在 4:21 排产、约 5:20 落地，**比第二段早 112 秒**。已修：显式优先级 `strongDef > aaDef > baseDef`，且只有真的排产成功才跳出循环。
- **反装甲塔被侧向轮转推离了敌方来向**：`placementCenter` 让防御塔按 `(k%3)-1` 做 −4/0/+4 格轮转以覆盖两翼，但唯一那座 ATESLA 因此落到基地正东，射程 8 够不到 9.2–20.1 格外的交战区，**8:47 才第一次挨打、8:49 阵亡**。已修：`strongDef` 强制压在轴线上。

另外修了两处会放大损失的：

- **侦察状态机**：军犬一死就永久 `scouted=true`。在"没侦察到敌基地防御就不许进攻"成为硬制度之后，**丢一只狗等于整局都不许进攻**——本局指挥官不得不手工重置状态机 3 次。已改为**有界重试 3 次、间隔 20 秒**，全败才放弃并警告。一只狗 200，瞎着打的代价是一整局。
- **矿车被强制重派进敌占矿区**：40 秒超时原本无条件把矿车派回去，本局 8:15/8:19 两次强制重派后三辆在 3–11 秒内被猎杀（8 辆 CMIN 的损失全部紧跟在"撤回"或"重派"之后 2–11 秒）。已修：目标矿区 12 格内仍有敌军就继续等待。矿车 1400 一辆、上限只有 6。反击反射也加了防守态几何约束（只在自家防御壳内还手），本局 4 次被防线外的矿车诱饵钓出塔线、目标距最近塔 13–18 格。

方案层 v013 改 2 个字段：`defenses.strongDef` 1→2、`minerEscort` 1→0（本局它**起反作用**：护卫恒取最快的那辆 FV 钉在矿区，8:01 全队只剩它、坐标就在矿区，同时敌方 SREF×2 在别处无人阻拦）。战术库新增 T-042（防空与反装甲的交换比必须分开核算——本局防空段 2.61:1、地面段 0.25:1，混算会得出"塔线没问题"的错误结论）与 T-043（"field 静止"不等于"空窗"：那 117 秒里敌方 army 从 4200 涨到 12300、碉堡从 2 座补到 5 座，是静默期加固换装）。

**match-015（v013 首战，赢棋，v013 → 不 promote，维持 v013）**：本系列第 5 胜，6:59，也是最快的一局。这一局的意义是**两批旧修复第一次同时兑现**：match-013 之前的"防御排产优先级"和 match-014 的"反装甲塔压在敌来向轴线"合起来让塔线全程零建筑损失；match-009 换掉判据的自动转攻反射，在 5:55 自己触发、5:56 出发、17 秒收尾，**第一次不需要人工兜底就带来胜利**（match-009/012 那次都得靠指挥官手动改 `stance`）。

指挥官本局的判断也值得记：5:12 对手一次性推出 12 单位/7230（含 6 架 JUMPJET）时，主动选择**不出门抢空窗、放它撞塔线**，结果 12 秒零损全歼；分析员 6:39 建议"进城后先集火拆掉 ATESLA 再打建造厂"，指挥官按 T-041 的判负口径**没有采纳**，直接打 4 类生产建筑，63 秒结束——复盘算账支持这个取舍（拆 ATESLA 不产生任何胜利进度，绕过去至少多花 10–15 秒，期间照样在它射程内挨打），但同时如实记下代价：**全局损失的 96.3% 都发生在最后 32 秒的攻城段**。

两处执行层问题由本局暴露并修复：

- **`siege()` 每 0.7 秒无条件重选目标**：它按"优先级 → 离部队质心距离"排序后直接覆盖当前目标，两个排序键都在动（行军途中质心漂移、建筑被打掉），于是同一优先级、分处敌基地两端的建筑会轮流当"最近"。本局 5:57 点名建造厂，6:42 才落下第一条 `[kill] 摧毁敌方建筑`——**46 秒没有战果**（其中 37 秒是行军），终局目标还漂到了对判负零贡献的电厂上。已修：**以优先级为界的粘性**——当前目标仍在、且它的优先级不高于本轮最优候选时继续打它，只有出现严格更优的等级或它被拆掉才换。
- **攻城期仍发"建筑队列已空闲，请追加"**：5:43（转攻前 12 秒）和 6:43（正在拆楼）各发一条，而那时资金是 0。文案指向的真正缺口（`buildOrder` 跑完没有兜底项）是改方案的事，不该在攻城期发号施令。已修：该提示只在**防守态、且资金 ≥1500** 时发出。

复盘还纠正了一处口径：本局实测 `game.rules` 的造价与档案不符（E2 = 90 不是 180、HTK = 500 不是 600），用旧值重算会把损失算成 11720 而不是 10310。对手侧的新发现是三条判据被推翻或改写：JUMPJET **首见只有 1 架**且首波是纯地面，"首见即 ≥3–7 架混编"不再成立（降为倾向）；"静默期"的判据改成看**它的在造成本斜率**而不是时长（本局 6 分钟静默期间它只涨了 1 个单位）；新增 T-044（判断它能不能掏出重单位，看 `GATECH` 建成时间 + 在出矿的矿车数）。战术库 T-017 升为硬要求、T-043 升为确认。

**match-016（v013 第 2 局，输棋，v013 → 不 promote，维持 v013）**：6:01 负，v013 变成 1 胜 1 负。组合与 match-014 完全相同（我方盟军 GA @71,118 vs 敌方盟军 @135,80），结果也一样是负，但输法不同。

```
│  runtime.js 执行层（每 250ms）：生产 · 放置 · 部队 · 反射 · 攻城 · 记录器          │
│      ▲ plan（按角色分配写权限）          │ intel（公平视野，每个读者独立游标）     │
└──────┼───────────────────────────────────┼─────────────────────────────────────────┘
       │ C.apply / C.advise                ▼
  ┌──────────┐   ┌──────────────┐   ┌────────────┐
  │ 指挥官   │◀──│ 情报分析员    │   │ 后勤官(可选)│   ← 实时 subagent（约 10–15 秒一轮）
  └──────────┘   └──────────────┘   └────────────┘
       │ 对局结束
       ▼
  ┌──────────────┐  归档 → 时间线 → 对手档案 / 战术库 → 下一代方案 → 执行层问题清单
  │ 复盘学习员    │─────────────────────────────────────────────────────────────────▶ 下一局
  └──────────────┘
```

设计要点：
- **反应和决策分层**：LLM 思考一轮要 10–30 秒，战斗却是秒级的。秒级反应（迎击、补电、修理、防空、撤退、集火建筑）由执行层完成；agent 只负责战略参数。
- **公平视野**：实时 agent 只能读我方可见的情报。全视野的记录器数据只在赛后复盘时使用。
- **进化数据和代码分离**：战绩、方案版本、对手档案、战术库保存在 `~/.claude/ra2-commander/`，升级 skill 不会丢失。

## 环境要求

- [Claude Code](https://claude.com/claude-code) **桌面版**（Code 标签页），需要内置浏览器面板（`mcp__Claude_Browser__*` 工具）来打开并注入游戏页面。
- **没有内置浏览器面板时也能跑**：任务书和 `references/ui-navigation.md` 里写了替代方案——用 Chrome 的 `--remote-debugging-port` 加一条本机 CDP 桥驱动页面，看屏幕则靠截图 + 反色放大 + OCR 认坐标。需要注意 Chrome 必须带 `--no-sandbox`（否则子进程沙箱初始化失败会直接崩掉）、且窗口可见高度要 ≥ 600，否则"开始游戏"按钮会被裁到屏幕外。match-015 全程用这套方案完成。
- Python 3.8+（运行 `scripts/*.py`）
- Node.js（可选，只用于 `node --check` 做语法检查）
- 已测试环境：gonghui.k0s.cn 客户端 v0.87.0，单机模式 → 遭遇战，AI-简单，地图"岛屿之战 (2)"。我方打过盟军（法国）和苏军；对手遇到过盟军、苏军、Confederation（古巴，第三阵营）三种，出生点会互换，双方也可能是同阵营镜像局（match-006/007 都是盟军 vs 盟军，match-010 是苏军 vs 盟军）；古巴对手已出现两次（match-005、match-008），节奏几乎逐秒吻合。

## 使用

在 Claude Code 桌面版里直接说：

```
打开 https://gonghui.k0s.cn/ ，用 ra2-commander 打一局遭遇战
```

或者更具体一些：

```
用 ra2-commander 打一局，开指挥官、情报分析员和后勤官三个 agent，打完复盘并进化方案
```

Claude 会按 `SKILL.md` 的流程执行：

1. `evolve.py init / status`：初始化数据目录，查看当前方案版本和战绩。
2. 在内置浏览器打开游戏，停在主菜单。
3. `evolve.py new-match`：生成本局目录、注入代码（install.js / arm.js）和各角色任务书，在**开局前**注入执行层。
4. 并行派出实时 agent（默认指挥官 + 情报分析员）。
5. 点击 单机模式 → 遭遇战 → 开始游戏。执行层第一秒接管，agent 实时指挥。
6. 对局结束后，派出复盘学习员：归档、更新对手档案和战术库、晋升新方案版本、列出执行层问题。
7. 向你汇报胜负、关键决策、对手的新打法和进化内容。

中途可以随时插话，例如"没有敌军就直接拆主基地和电厂"。Claude 会把指令转成方案修改，或者给执行层打补丁。

### 常用命令

```bash
S=~/.claude/skills/ra2-commander/scripts
python3 $S/evolve.py status                                   # 方案版本谱系和战绩
python3 $S/evolve.py new-match --opponent ai-easy --map "岛屿之战 (2)" --roles commander,analyst,quartermaster
python3 $S/evolve.py record --match match-004 --result won --duration 430
python3 $S/evolve.py promote --candidate candidate.json --reason "T-005: 更早出击"
python3 $S/evolve.py use v002                                 # 回退到某个方案版本
python3 $S/summarize_match.py ~/.claude/ra2-commander/matches/match-004
```

数据目录可以用环境变量 `RA2_DATA` 指定。想从头开始，删掉 `~/.claude/ra2-commander/` 再运行 `init`，会重新从种子数据初始化。

## 仓库结构

```

scripts/summarize_match.py  赛后数据 → 双方时间线
agents/commander.md         实时：指挥官

agents/quartermaster.md     实时（可选）：后勤官
agents/learner.md           赛后：复盘学习员
references/plan-schema.md   方案字段、反射、角色权限、情报接口
references/game-api.md      引擎接口、枚举、单位名、坑点清单、游戏更新后如何重新逆向
references/ui-navigation.md 菜单操作
assets/seed/                初始经验：方案 v000–v013、对手档案、战术库、十六局记录（含每局全部复盘产物）

```

## 扩展

- **加角色**：在 `agents/` 下写任务书模板，在 `runtime.js` 的 `C.ownership` 里给它分配方案字段；只提建议的角色用 `C.advise`，不需要改代码。可以参考的方向：侦察官、空军官、微操官。
- **打更强的 AI**：`new-match --opponent ai-medium`，会建立独立的对手档案。
- **游戏更新后接口失效**：按 `references/game-api.md` 第 8 节重新定位接口。

## 使用规则

- **只用于单机模式对战电脑 AI。** 不要在排位赛或联机大厅里使用：对真人使用自动化就是作弊，skill 本身也会拒绝。
- 请尊重游戏站点和社区，不要高频刷局，也不要做任何影响服务器的操作。
- 本项目通过读取客户端内存对象、调用游戏自带 AI 使用的同一套命令接口来操作，不修改服务器，也不包含或分发任何游戏代码和素材。
