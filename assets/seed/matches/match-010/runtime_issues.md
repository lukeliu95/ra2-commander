## 1.（关键，本局最高优先级）矿车被"撤回基地"反射派回后，永远不会被重新派去挖矿——指令队列清空即永久闲置；主会话已现场手动修正一次，需要代码层永久修复

- **现象**：`army()` 里的 `exposedMiners` 反射（`runtime.js:421-427`）——矿车血量 <95% 且附近有威胁、但威胁本身还没进入迎击判定（`threats`）——会执行 `orderThrottled(exposedMiners, ORD.Move, base.x, base.y, 'minerHome', 8)`，把矿车派回基地坐标，并记一条 `[reflex] 矿车在防线外被打：撤回基地（N 辆），部队不出防线`。**通读整个 `runtime.js`，没有任何地方会在此后重新给这些矿车下达"回矿区挖矿"的指令**——矿车收到显式 `ORD.Move` 后，游戏引擎不会自动恢复其采矿 AI（`harvesterTrait` 不会因为原地闲置而自己重新出发去挖矿），指令队列清空后就永久停在基地里，形同报废。
  本局该反射触发 **3 次**：3:43、3:57、4:40，各撤回 1 辆矿车（`log.json` seq 102/110/128）。主会话在游戏进行中（约 t=310，5:10）现场核实：5 辆矿车里 **4 辆** `unitOrderTrait.orders` 为空、`harvesterTrait.harvestedAmount` 为 0，坐标全部堆在基地附近（71,116 / 69,116 / 73,116 / 70,116），与 3:43/3:57 两次撤回事件的时间点吻合（**4 辆里有 1 辆无法用这 3 次日志直接对应上，可能是更早一次未被捕获到的撤回，或是新造出来但从未真正派往矿区的矿车——两种可能都指向同一个根因：矿车一旦被显式 `Move` 过或从未被显式派过矿，都不会自发去挖矿**）。主会话用 `C.my.orderUnits(id, ORD.Move, oreTile.x, oreTile.y)` 把这 4 辆手动派回 `M.oreTiles` 里的矿格，25 秒后核实矿车已移动到矿区附近、资金从 0 回升到 1060，确认修复生效。此后到判负（6:56）`log.json` 里再没有出现新的"矿车在防线外被打"事件，说明手动干预期间没有再触发这条反射。
- **影响程度：关键，是本局经济雪崩的重要推手之一**。`snapshots.json` 显示我方 `HARV` 数量从 **3:22（t=202，5 辆）起一路冻结到 6:23（t=383，仍是 5 辆）**，长达 **3 分钟**，`targetRefineries:4`/`minersPerRefinery:2`（目标 8 辆矿车）从未接近达成；同期资金几乎全程为 0（t=222 到 t=383 之间只有 t=182/242 短暂正数），敌方同期资金稳定在 300-3400 之间波动、从未见底。**这段经济停滞窗口正好横跨"JUMPJET 首波被击退"和"MGTK/SREF 第二波到来"之间的关键恢复期（4:13-5:48）**——commander 在 debrief 里明确指出，第二波来袭时我方 army 只恢复到 9-10 单位/2430-2930（远不足以对抗 5400-11250 价值的地面波），经济迟迟无法充分复苏是原因之一，而矿车闲置正是"明明有矿区可挖、却挖不到钱"的直接执行层缺口。
  **粗略估算经济损失**（方法：受影响矿车的闲置时长 × 正常矿车产出速率，量级参考，不是精确值）：3 次触发的矿车分别闲置了约 87 秒（3:43 触发，至 5:10 手动修复）、73 秒（3:57 触发）、30 秒（4:40 触发），合计约 **190 矿车·秒** 的产能空转；按本局其余矿车的实际产出粗估（同期资金曲线里能观察到的单次矿车入账在几百到上千不等，一次完整往返周期约 20-30 秒），这 190 秒大约相当于 **6-9 个往返周期的产出被浪费**，量级在 **1500-3000 credits** 左右——这还只是被日志直接记录的 3 辆，如果第 4 辆（主会话现场发现、日志里找不到对应触发事件）在更早时候就已经闲置，实际损失会更高。这个量级足以解释部分"资金持续为 0、无法在两波之间重建军力"的现象，但不是唯一原因（TESLA 3:26 阵亡、NAREFN 建筑本身也被摧毁过 2-3 次同样在消耗经济）。

  **结论：这条反射至少在 match-005/007/008/009 四局里也触发过，且触发后受影响矿车所在的"矿车总数"曲线都表现出同一种模式——触发后不再增长，直到局末**。此前没有一局像 match-010 这样被主会话现场用 `unitOrderTrait`/`harvesterTrait` 直接核实到"指令队列为空、采矿量为 0"，所以一直被当成"经济曲线正常的正常波动"，**这是一个至少存在了 5 局、被长期忽视的执行层缺口**，只是本局第一次被抓到并临时修正。
- **推测原因（已对照代码）**：`army()`（`runtime.js:421-427`）里 `exposedMiners` 只负责"发现受伤矿车 + 派回基地 + 记日志"三件事，函数返回前没有任何逻辑去跟踪"这批矿车之后要不要、什么时候重新派出去"。`production()`（新矿车下线时大概率会被引擎自动指派去挖矿——这也是为什么从来没被怀疑过，"新矿车会自动开始挖矿"掩盖了"被撤回的旧矿车不会恢复"这个不对称行为）和 `army()` 的其余分支（`threats`/`attack`/`harass`/`minerEscort` 的 escort 分支）都不会引用这些矿车的 id，它们唯一收到的指令就是那一次 `ORD.Move` 回基地，之后完全脱离 runtime 的管理，直到玩家/agent 手动介入。
- **建议代码改法（指到函数名，供主会话下一轮实现）**：
  1. 在 `M`（运行时状态对象）上新增一个 `M.retreatedMiners`（`Map<id, {t: 时间戳}>` 或 `Set`），`army()` 里 `exposedMiners` 触发撤退时，把这些矿车 id 连同触发时刻一并写入这个表，而不只是发指令和写日志。
  2. 在 `army()` 每个 tick 的适当位置（建议紧跟 `exposedMiners` 判断之后，或独立成一小段，逻辑上属于"矿车管理"而不是"部队接战"）新增一段"矿车复工"检查：遍历 `M.retreatedMiners` 里记录的矿车 id，对每一个仍然存活的矿车，如果 (a) 血量已恢复到某个阈值（比如 ≥90%，呼应 `hurtMiners` 判定用的 95% 附近的量级）**且** (b) 矿车当前位置附近（比如复用 `nearBuilding`/`threats` 已有的判定半径）没有敌方非建筑单位（即威胁已解除），就用 `orderThrottled([miner], ORD.Move, spot.x, spot.y, 'minerResume:'+id, 8)` 把它重新派回最近的矿格（`spot` 直接复用 T-026 修复里已经写好的 `oreNear(refPts[i]) || refPts[i]` 逻辑，或者更简单地找 `M.oreTiles` 里离该矿车当前位置最近的一个），然后把这个 id 从 `M.retreatedMiners` 里删除。
  3. 兜底：如果矿车已经在基地附近待了超过一定时间（比如 30-45 秒）还没有被判定为"可以复工"（威胁一直没解除），也应该强制重新派一次（即使威胁还在，继续挖矿至少比原地闲置好，参考现有"防线外的矿车撤回基地"这条本身就是"接受一定风险"的取舍），避免极端情况下矿车永久卡在"血量卡在 90-95% 之间反复横跳、永远不满足复工条件"的边界。
  4. 矿车死亡或被摧毁时要记得从 `M.retreatedMiners` 里清理，避免表越攒越大（`units`/`raw` 列表本身每 tick 都是重新从 `S` 取的，可以在遍历时用 `units.some(u => u.id === id)` 之类的判断顺手做垃圾回收）。

## 2.（次要，已知局限）`defendMinValue` 在开局阶段部队总值天然偏小时会误触发"撤退"，即使当时正在打赢

- **现象**：1:18、1:34、1:43 三次交战，我方部队价值（`myValue`）都是 720（8 个 E2，无载具），低于 `defendMinValue` 的默认值 800，`army()`（`runtime.js:480`）里 `myValue > 0 && myValue < (P.defendMinValue ?? 800)` 这个条件被触发，三次都记了一条 `[reflex] 防守交战只剩 100%（价值 720）：撤回基地`——**注意 `defendRatio` 打印出来是 100%，也就是这场交战根本没有发生任何战损（`M.defend.value` 就是当前 `myValue`，没有变化）**，同期我方对拴绳内的单个 E1/ADOG 是零损失全歼（1:22 杀 E1、1:36 杀 ADOG、1:46 再杀 E1），并不存在真实劣势。
- **影响程度：低**。本局代价很小——反正威胁马上就解除了，"撤回基地"这个动作本身没有额外损失，只是行为上不合理（明明打赢了却"撤退"）。但这是一个方向性错误的信号：如果未来某局开局阶段的部队规模进一步压缩（比如更保守的 `infantryCap`），或者敌方在开局阶段真的持续派出多个单位试探，这条绝对值判断可能会更频繁地打断本该继续的有利交战。
- **推测原因**：`defendMinValue` 是纯绝对值判断，不看这场交战是否真的产生过战损、也不看 `defendRatio`（比例判断）是否同时告警。它是 match-008 复盘后加的"补丁"，用来防止"残部基数很小时比例判断在两次采样间被跳过"的问题（见 tactics.md T-029），但没有考虑"部队总值本来就小、且完全没有战损"这种开局阶段的常见场景——`myValue < 800` 在开局阶段（步兵还没配齐、载具还没下线）几乎是常态，不代表"打不过"。
- **建议代码改法（指到函数名，供主会话评估，优先级低于问题 1）**：在 `army()` 的 `defendRatio`/`defendMinValue` 判断（`runtime.js:479-483`）里，给 `defendMinValue` 那一支路加一个"这场交战确实发生过战损"的前提条件，比如同时要求 `defendRatio < 1`（即 `myValue` 相对交战开始时的 `M.defend.value` 确实下降过，哪怕只降了一点点），或者要求本场交战期间已经有至少 1 次 `loss` 事件。这样 `defendMinValue` 仍然能在"残部基数小、真被打疼"的场景下兜底（match-008 的用例不受影响），但不会在"部队总值天生就小、且正在打赢"的场景下误触发。
