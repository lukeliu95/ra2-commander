### 7. 迷雾记忆对象（仍存在，本局拿到确凿证据）

- **现象**：我方侦察犬 0:54 阵亡后，敌方半场再没有任何我方视野单位（我方所有单位全程在 (69–82,108–121) 一带），但 `visibleArmy` 仍持续报出敌方单位：

  - 4:02–4:07 报 2 单位 @(131,82)→(122,85)；
  - 5:00–5:03 报 1→3 单位 @(133,82–83)，**`typesFirstSeen.APOC = 4:46` 就是在这片无视野区域"看到"的**。
- **确凿对照**：全视野快照 t=121（2:01）敌方 `army: {count: 12, value: 1190, at: {x:131, y:84}}` —— 与实时 `visibleArmy` 报的**数量、价值、坐标完全一致**。
- **性质判定**：不是"静态残留"（位置和数量会随时间变化，4:02 那次还在移动），而是 **`g.getVisibleHostileObjects(player)` 按"已探索（去雾）"而不是"当前有视野"返回对象，并且给的是实时坐标**。佐证：5:01 时全视野里敌方作战单位有 8 个 @(141,85)，而 `visibleArmy` 只报 3 个 @(133,82) —— (141,85) 在侦察犬从未走到的区域，所以被挡住了。**即：凡是侦察犬 0:34–0:54 走过并去雾的那片，之后一直能"透视"。**
- **影响**：
  - 对 `visibleArmy` 是**污染**：敌方在家生产/防守的单位被算进"可见部队"，让 `distToMyBase` 和 `trend` 彻底失去意义（见 #4）。
  - 对 `typesFirstSeen` 反而是**白送的科技侦察**：本局 NARADR 1:08、NANRCT 2:40、NADEPT 3:08、APOC 4:46 的"首见"多半来自这条路径。情报员据此做出了本局最有价值的几条预警。**所以不要一刀切地把它过滤掉。**
- **建议改法**（`C.state()` / `intelSample()` / `C.intel()`）
  1. 保留 `enemyBuildings` / `enemyTypes` 的现有行为，但在情报输出里把它们标注为"含迷雾推断"，让角色知道这不是"真的看见了"。
  2. `visibleArmy` 增加一个按当前视野过滤的版本（用 tile 的 fog 接口，或退而求其次：排除距敌方出生点 < 25 格的单位，和 `lead` 的 15 格规则统一），或者直接把 `visibleArmy.distToMyBase` / `trend` 从情报里删掉，只保留 `lead`——本局证明角色只需要 `lead`。
  3. 给每个敌方对象记 `lastSeen` 并在情报里输出，让角色自己判断新鲜度。

## B. 本局新发现的问题

### 1. 资金为 0 时，四条生产队列同时排产，谁也造不完（影响：**高，本局第二大败因**）
- **现象**
  - 4:15 排产 `TESLA`（1500）→ 6:28 进度 52% → 7:16 进度 68% → 7:38 仍只有 66%（被打掉过血）。**整整 3 分 23 秒，一座反装甲建筑都没落地**，约 990 资金沉没。
  - 同期 `HTNK` 6:28 进度 17%、7:16 进度 43%；`DRON` 权重从 4:09 的 1 一路提到 7:58 的 5，**一辆都没造出来**。
  - 我方资金：1:20 起到终局基本恒为 0（25 张快照里 17 张为 0，其余最高 1430）。
- **推测原因**：`production()` 里三条队列的排产门槛都能被警报绕过——
  - Armory：`dq.status === Idle && currentSize === 0 && (pd.credits > 700 || M.alarm)`
  - Vehicles：`pd.credits > 600 || (Structures 队列空闲) || M.alarm`
  - Infantry：`infCount < P.infantryCap && (pd.credits > 300 || M.alarm)`

  本局 **`M.alarm` 为 true 的时间占全局 46%（220/477 秒）**，包括 6:36–7:57 连续 81 秒。于是在资金为 0 的整个中后期，四条队列一直同时有在建项，把每一笔进账瓜分掉，最贵的那一项（1500 的 TESLA）永远排在最后完成。
- **建议改法**（`production()`）
  1. **警报只应绕过"便宜且能立刻上防线"的东西**（步兵、坦克），不应绕过 ≥1000 的建筑/防御。给 Armory 分支加成本判据：`pd.credits > Math.min(700, r.cost * 0.5) || (M.alarm && r.cost <= 700)`。
  2. 加一个**资金预留**：当 Armory / Structures 有在建项且 `pd.credits < 300` 时，暂停 Infantry 队列（`setQueueStatus` OnHold 或干脆不排产），保证贵的那项能收敛。
  3. 或者更简单：全局限制"同时在建的队列数 ≤ 2"，按 `stance` 决定优先级（defend：Armory > Vehicles > Infantry > Structures）。
- **对胜负的影响**：这是"整局零反装甲建筑"的直接技术原因。方案层已用 v004 的 `defenses.strongDef: 1`（让 TESLA 在 1:50–2:30 还有钱时排产）绕开，但**代码层的坑还在**，下一局指挥官中途补任何贵建筑仍会踩。

### 2. `buildOrder` 跑完后建筑队列长时间空转（影响：中）
- **现象**：2:50 放置最后一座 NAPOWR 后，buildOrder 九项全部完成，**Structures 队列从 2:50 一直空闲到 5:14**（2 分 24 秒），期间只有 4:15 的 Armory 排产。这正好是 T-019 说的"静默期投资窗口"，但执行层没有任何默认动作。
- **推测原因**：`production()` 的兜底只有三条：补矿厂到 `targetRefineries`、补工厂到 `maxFactories`（需 credits > 2500）、补电厂（powerLeft < 150）。三条本局都不满足，于是完全空转。
- **建议改法**：buildOrder 跑完且队列空闲超过 N 秒时记一条 `warn`（"建筑队列已空闲 N 秒，plan 没有后续项"），把决策权明确交还给指挥官——本局指挥官直到 5:14 才注意到。代价极小。

### 3. `reconcileQueues` 不看 `infantryCap`（影响：低–中）
- **现象**：7:13 指挥官把 `infantryCap` 12→6、7:58 改成 0，理由都是"步兵对 3 辆天启毫无意义，钱要留给 HTNK/DRON"。但 `reconcileQueues` 的 Infantry 分支只判断 `sumFor(P.infantryMix, name) > 0`，`E2` 权重始终 > 0，所以**已排队的步兵一个都没被取消**。
- **推测原因**：`need[Q.Infantry]` 缺少 `infCount < P.infantryCap` 这一层判断（`production()` 排产时有，对账时没有）。
- **建议改法**：`reconcileQueues` 增加一个 `infCount` 入参，Infantry 分支改成 `(it.rules.name === R('dog')) || (sumFor(P.infantryMix, it.rules.name) > 0 && infCount < P.infantryCap)`。`infantryCap: 0` 应该能立刻清空步兵队列。
- **备注**：本局终局大量的 E2 损失**不是**这个 bug 造成的，见下面 #5。

### 4. 赛后记录器把弹体算进敌方 `army.count`（影响：低，只污染归档）
- **现象**：`snapshots.json` 里敌方 6:01 / 7:01 / 7:41 / 7:57 四张快照的 `units` 含 `V3ROCKET`，并被计入 `army.count`。7:41 那张 count=14，实际作战单位 12。
- **推测原因**：`record()` 用 `isCombat()` 过滤，而 `isCombat` 只排除建筑、矿车、基地单位和工程师，**没有排除弹体**（实时路径是靠 `C.state()` 里的 `!isMissile(o)` 挡住的）。
- **建议改法**：`record()` 里的 `armyUnits` 改成 `u.filter(o => isCombat(o) && !isMissile(o))`；`units` 字段可以保留弹体，但最好也过滤掉，否则 `timeline.md` 的"首次出现"表会把 V3ROCKET 当成一种单位列出来（本局就列了）。

### 5. `C.intel({detail: true})` 在我方建筑被拆光后抛异常（影响：低，但局末失明）
- **现象**（可复现，刚刚在页面上复验过）：终局调用 `C.intel({detail:true})` 抛 `TypeError: Cannot read properties of undefined (reading 'buildings')`；`detail:false` 正常返回。情报员 8:01 撞到过同一个异常。
- **推测原因**：`detail` 分支里的 `avail()` → `player.production.getAvailableObjects()`，我方 owner 的 buildings 已为 undefined 时游戏侧抛错。
- **建议改法**：`C.intel()` 的 detail 分支整体包 try/catch，失败时 `out.available = []` 并附一条说明，不要让整个情报调用挂掉。

### 6. 已排除的"疑似问题"：我方凭空出现的 `ENGINEER`（结论：不是 bug）
- **现象**：指挥官记录里提出 7:38 情报的 `me.units` 出现 `ENGINEER:1`，而 plan 的 `infantryMix` 从未含工程师、也没有对应的排产事件。
- **核查结论**：这是**建筑被摧毁时逃生的驻员（RA2 的 Survivors 机制）**，不是归属判定错误。证据是损失事件的时间耦合：7:36 `NACNST` 被拆 → 7:41 损失 `ENGINEER`（建造厂的驻员就是工程师）；7:32 `NAPOWR` → 7:33 E2；6:45 `NAREFN` → 6:50 E2；7:45 `NAHAND`、7:48 `NAWEAP`、7:53 `NAPOWR` 之后各跟着 1–2 个 E2 损失。全局 41 个 E2 损失里，7:36 之后的 11 个基本都是这类驻员。**无需改代码**，但 `infantryCap` 用的 `S.mine.filter(o => o.isInfantry()).length` 会把这些驻员算进上限，属于可以接受的小偏差。
