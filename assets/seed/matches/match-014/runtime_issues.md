## 1. 防御排产循环的 `break` 写错位置 + `defenses` 的键序被当成了优先级 → 第 2 座反装甲塔被结构性饿死

**现象（时间 + 数据）**

- 全局面板里只有 **1 条** `[build] 排产防御 ATESLA`（2:42，那次还是靠 `敌方逼近` 绕过了资金门槛），此后到判负 **0 条**。
- 指挥官 **7:40 确实执行了变更**：`{"defenses":{"baseDef":4,"aaDef":2,"strongDef":2}, "buildOrder":[...,"strongDef"(第11位),"aaDef","refinery","tech","depot"]}`；
  同一批改动里的 `baseDef 3→4` 部分在 **8:24** 排产了一座 `GAPILL`（日志：`排产防御 GAPILL（500，资金 0）`），
  而 `strongDef 1→2` 部分在随后 **86 秒里没有产生任何 ATESLA 排产事件**。
- 8:24 那座 GAPILL 到 9:06 判负 **都没有 `放置防御 GAPILL`**（快照 8:21=3 座 → 8:42=2 座，与「3 座 - 8:42 的 1 次损失」吻合，说明第 4 座从未落地），也没有 `找不到 GAPILL 的位置` warn。
- 结果是 7:12 第二段（MGTK/SREF）来袭时，我方仍是**单座 ATESLA**，而它在 7:16–8:43 全程射程外（见 #2）。

**根因（代码）** `production()`，install.js:276–285：

```js
for (const [role, n] of Object.entries(wantDefenses(P, av))) {
  const name = R(role);
  if ((counts[name] || 0) >= n || !av.has(name)) continue;
  ...
  if ((pd.credits > 700 && pd.credits >= c * 0.5) || (M.alarm && c <= 700) || urgent) { my.queueForProduction(...); log(...); }
  break;          // ← 在 if 之外：第一个「未满足」的角色无论排没排上，循环都结束
}
```

`wantDefenses`（install.js:178–182）返回 `{...P.defenses}`，键序就是 plan JSON 的书写顺序 → v012 是 `baseDef, aaDef, strongDef`。
于是 **strongDef 只有在 baseDef 和 aaDef 都已满足时才会被求值**。7:40 把 `baseDef 3→4` 和 `strongDef 1→2` 写进同一个对象，
等于「顺手把排在 strongDef 前面的那道门永久焊死了」——baseDef 从此永远 `3 < 4`，`break` 每次都停在它身上。

另外 `(M.alarm && c <= 700)` 这条快速通道对 ATESLA **永远不可能生效**（`c = 1500 > 700`），
所以 strongDef 只有 `credits > 700 && credits >= 750` 或 `strongUrgent`（`groundNear && credits >= 450`）两条路。
本局 `defend` 期间的 alarm 只出现在 0:54–5:03 和 8:24 之后，7:40–8:23 完全没有 alarm。

**反事实（为什么这不是「本来也没钱」）**
把 `strongDef: 2` 写进**初始 plan**（v013 已改），则在 baseDef 3/3、aaDef 2/2 均已满足、Armory 队列自 3:39（ATESLA#1 落地）起一直空闲的前提下：

| 时间 | 我方资金 | 快照 |
|---|---|---|
| 4:21 | 980 | >700 且 ≥750 → 门槛通过 |
| 4:41 | 1189 | 同上；且 4:45 有 `敌方重型单位正在基地附近逗留` warn（groundNear → strongUrgent 也成立） |
| 5:01 | 1060 | 同上 |

**4:21–5:01 是全局唯一一段资金 >750 的窗口**（29 张快照里资金 ≥750 的只有 t=1/21/41 的开局与 4:21/4:41/5:01）。
按 ATESLA 的实测工期（2:42 排产 → 3:39 放置，57 秒）推算，ATESLA#2 约 5:20 落地，比 7:12 的第二段早 **112 秒**。

**建议改法**
1. 把 `break` 移进 `if`：`if (gate) { queue; log; break; }`，让循环在第一个角色过不了门槛时继续尝试下一个（Armory 队列单槽，一次 tick 仍只会排一项）。
2. 更明确地把优先级写进代码而不是依赖 JSON 键序：`wantDefenses` 返回**有序数组**，顺序 `strongDef > aaDef > baseDef`（反装甲 > 防空 > 碉堡，因为前两者有造价门槛、后者的快速通道 `c<=700` 本来就是最宽的）。
3. 顺带：`M.alarm && c <= 700` 这条通道对 ≥1000 的防御永远无效，把阈值改成 `c <= 700 || strongUrgent || aaUrgent` 已经有类似分支，建议统一成一个 `canAfford(c)` 函数。

**⚠ 不要用「把 strongDef 挪到 defenses 第一个键」来绕过**：本局前 4 分钟 strongDef 是 1/1 已满足所以没事，
但一旦它变成 2/1 不满足而资金为 0（本局 15/29 张快照资金为 0），`break` 会停在它身上，
`aaDef`/`baseDef` 将永远轮不到——第 2 座 NASAM（0:59、2:38 落地，正是它顶住了 3:43 起的 12 架 JUMPJET）就不会存在。已在 v013 的 promote reason 里明确否决。

## 2. `strongDef` 塔的放置被 `side = (k % 3) - 1` 轮转推离敌方来向 → 唯一反装甲塔全场射程外

**现象** `placementCenter()`（install.js，`rules.isBaseDefense` 分支）：

```js
const k = buildings.filter(b => b.rules.isBaseDefense).length;
const side = (k % 3) - 1;                       // -1 / 0 / +1 循环
return {x: base.x + dir.x*P.defenseDistance - dir.y*side*4,
        y: base.y + dir.y*P.defenseDistance + dir.x*side*4};
```

我方基础建筑中心 ≈ (72.7, 118.2)，`enemyDir` 指向东北 (135,80)。
本局防御建造顺序：GAPILL(k=0) / GAPILL(k=1) / GAPILL(k=2) / NASAM(k=3) / NASAM(k=4) / **ATESLA(k=5 → side=+1)**。
side=+1 的垂直偏移 `(-dir.y*4, dir.x*4) ≈ (+2.1, +3.4)` 是朝**东南**转的，于是 ATESLA 落到了 **@79,118 = 基地正东 6.3 格**，
而地面来向是东北。

**代价（快照/日志交叉）** 第二段（7:16–8:43）的威胁点依次是 (91,105)→(85,106)→(81,107)→(80,110)，
距 ATESLA(79,118) 分别是 **20.1 / 18.4 / 11.2 / 7.1** 格，而 ATESLA 射程 **8**。
第一次挨打是 **8:47**（`反击：ATESLA 正在挨打…@80,111`），**8:49 阵亡**。
也就是说，我方**唯一**能高效点掉 MGTK/SREF 的火力（PrismWarhead 120 伤、对 light/heavy 都是 1.0，
杀一辆 200HP 的 MGTK 只要 2 发 ≈ 8 秒）在整段决定性交火里几乎没有输出。

**建议改法** 在 `placementCenter` 里对 `R('strongDef')` 强制 `side = 0`（压在 enemyDir 轴线上），
或把 side 轮转的范围缩到 ±1 格而不是 ±4 格。防空塔（NASAM，射程 12）轮转问题不大，反装甲塔（射程 8）不能轮转。
