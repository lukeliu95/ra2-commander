## 2. 三个需要重点量化的问题（直接结论）

### (1) 防空的成功 / 第二段的失败如何分割

见「关键 1」：P1 = 2.61:1 有利（3380 : 8810，零建筑损失），P2 = 0.25:1 崩盘（36380 : 9050）。
**P2 占全局损失的 88.6%**。防空基建 3000 元换回 6 架 JUMPJET（3600）+ 基地 5 分钟，**不是白花钱**。

### (2) 反装甲为什么始终只有 1 座 —— 是「指挥官没做」还是「做了被吞掉」？

**指挥官做了，而且改了两次（5:31 把 `strongDef` 写进 buildOrder 第 14 位；7:40 提到第 11 位并把 `strongDef` 1→2）**，
但 **ATESLA#2 连「排产」都没进过**（全局面板 1 条 `排产防御 ATESLA`，就是 2:42 那次）。
不是资金问题单独造成的，而是**代码结构问题**（详见 `runtime_issues.md` #1）：

- `production()` 的 `for (const [role,n] of Object.entries(wantDefenses(P,av)))` 把 `break` 写在 `if` **外面** →
  只有第一个「未满足」的角色会被求值，它过不了资金门槛就 `break`，后面的角色一次都不看。
- `wantDefenses` 返回 `{...P.defenses}`，键序 = plan 里的书写顺序 = `baseDef, aaDef, strongDef` → **strongDef 永远排最后**。
- **7:40 指挥官把 `baseDef 3→4` 和 `strongDef 1→2` 写在同一个对象里** → baseDef 从此永远 `3 < 4` 不满足 →
  `break` 每次都停在 baseDef 上 → strongDef 在随后 **86 秒里 0 次被求值**。
  （同一批改动里 baseDef 的部分在 8:24 排产了一座 GAPILL，而它到 9:06 判负**都没放置**——即 `baseDef 3→4` 本局产出为 0，却把 ATESLA 锁死了。）
- 另外 `M.alarm && c <= 700` 这条绕过资金门槛的快速通道**对 ATESLA 永远不成立**（c=1500）。
  本局 7:40–8:23 完全没有 alarm（`defend` 期间 alarm 只在 0:54–5:03 与 8:24 之后出现），唯一通路只剩 `credits > 700 && credits >= 750`。

**资金窗口核算（回答「是不是资金吞掉的」）**：29 张快照里，4:00 之后资金 ≥750 的只有 **4:21（980）/ 4:41（1189）/ 5:01（1060）** 三点，
而这三点的 baseDef 3/3、aaDef 2/2 都已满足、**Armory 队列自 3:39 起一直空闲**。
所以：**如果 `strongDef: 2` 一开始就写进 plan，ATESLA#2 会在 4:21 排产、约 5:20 落地（实测工期 57 秒），比 7:12 的第二段早 112 秒。**
这就是 `strongDef: 1 → 2` 写进初始 plan 的数据依据（不是感觉）——它必须**预置**，因为唯一有闲钱的窗口出现在开局 4 分钟后，
而那时生效的前提是「strongDef 已经是 2、baseDef 没被人为抬到 4」。

**明确不改 baseDef**：3 座 GAPILL 用 SA 50 伤对 MGTK（light）25/发还可以、对 MTNK（heavy）只有 12.5/发；
7:40 的 `baseDef 3→4` 本局产出 0 且是锁死 ATESLA 的直接原因。v013 保持 `baseDef: 3`。

### (3) 经济为什么整局为 0

见「关键 3」。一句话：**6 辆的矿车上限 + 8 辆矿车被猎杀**（敌方 11 辆、0 损失，累计产出约 1.4–1.5×我方），
再叠加「撤回反射 → 矿车 AI 被取消 → 看门狗救回」的循环把剩余的采矿时间也切碎了。
`minerEscort:1` 没有任何正面作用，反而把最快的 FV 钉在矿区（8:01 全队只剩那 1 辆 FV、就在矿区）。

**主动否决的候选（避免下一轮重复试错，均已量化）**：
- `minersPerRefinery 2→3`（上限 6→9）：按本局实测回本速度（累计采矿约 4.0 万 / 546 秒 / 平均 3.4 辆 ≈ 每辆每 100 元 21 秒），
  第 4–9 辆矿车中的 3 辆（4200）要到 **7:56** 才回本，晚于 7:12 的第二段；而且矿车与坦克共用 `vq` 队列，
  这 4200 等于少 5 辆 MTNK ——正是 T-016 记录的 match-005 翻版。**不改。**
- `infantryCap 8→4`：E1 对 MGTK 要 27 发/36 秒、对 MTNK 要 80 发/106 秒（上式），本局 18 个 E1 阵亡 = 3240 = 全局损失 7.9%；
  但 v012 否决它的理由（写死进默认值会伤害苏军 20 E2 首波，T-020 的设计是「确认阵营后再降」）本局依然成立。**不改。**
- 把 `strongDef` 挪到 `defenses` 第一个键来绕过 `break`：**明确否决**——一旦 strongDef 不满足且资金为 0（15/29 张快照为 0），
  `break` 会停在它身上，aaDef/baseDef 永远轮不到，第 2 座 NASAM（顶住 12 架 JUMPJET 的那座）就不会存在。

3. **矿车 0 损失**：4:41 之后 CMIN 一路从 8 → 9 → 11 并保持到判负，**我方没有任何一次击杀它的矿车**（kill 里 0 条 CMIN）。
   对照 match-011/012 我方分别杀它 11 辆——**本局我方全程 0 次进攻，所以 T-036「顺路杀矿车」本局完全不适用**。
4. 空军补产能力在本局**被自己的经济限制**：5:21–7:21 一架 JUMPJET 都没补，7:21 之后才恢复（7:41=1 → 9:06=9 架），说明它的 GAAIRC 在第二段优先给了地面重甲。

## 5. 一条重要的**负面**结论：本局「一次进攻都没发起」是**正确**的，不是失误

任务书要求明确记功的一条：分析员 3:17 / 5:40 / 6:00 三次给出「转攻前置条件」，
明确指出 `knownBuildings` 为空**不是**因为敌基地是空的、而是因为我们一点视野都没有，指挥官采纳，全局 0 次进攻、 stance 全程 defend。
**本局数据支持这个克制是对的，甚至 7:01 那条「推掉那几架静止 JUMPJET」的建议如果执行会是灾难**：

| 时间 | 我方 | 敌方（全视野总数 / field 位置） |
|---|---|---|
| 7:01 | 18 单位 / **8340** | **12300**（JUMPJET 7 + MGTK 3 + SREF 1 + FV 2），质心 (127,88) 在家 |
| 7:21 | 18 单位 / 8340 | **13050**，质心 (97,99) 已推进 |

7:01 出击 = 用 8340 去撞 12300 + 5 座 GAPILL，比值 **0.68:1** —— 这是 match-013（0.36:1 那次）的同型剧本。
**所以「静默期 = 转攻窗口」这条（T-019/T-024/T-031）需要一个前置条件：先确认它家的静态防御和在造成本。**
本局它的 army.value 在静默期里单调上涨（4200→13050）且补了 3 座碉堡，是明确的「不要转攻」信号。
