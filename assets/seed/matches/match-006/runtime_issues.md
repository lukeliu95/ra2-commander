  3. 如果条件允许，`over` 判定后可以考虑暂停 `clearInterval` 之外的某种"保活"机制，防止赛后立刻被导航。

## 2. 用户指示 2 核实：`pt` 迎击点质心抖动导致 `AttackMove` 指令频繁重发 —— 代码改动已审阅合理，但本局未验证

- **代码审阅**（`node --check` + `git diff`）：
  - `node --check /Users/lukeliu/.claude/skills/ra2-commander/scripts/runtime.js` → **语法通过**。
  - `git diff` 显示改动位于 `army()` 第 410–419 行附近（搜索注释 "match-006 ground down 9 MTNK this way" 可定位）：原代码 `pt` 直接用 `Math.round(...)` 取整到整数格；新代码先算出浮点精确坐标 `ptRaw`，再 `Math.round(x/2)*2` 取整到 **2 格网格**。改动本身逻辑清晰、风险可控（只改变了取整粒度，不改变迎击点的整体方向和 `capR` 逻辑），**审阅结论：合理**。
  - 理论验证：`orderThrottled(units, type, x, y, key, s)`（约第 106–113 行）的节流 key 是 `key + ':' + x + ',' + y` 的精确字符串，只要 `x,y` 变了就是新 key，即使没超过节流秒数 `s` 也会重新下达指令（`lo.k !== k` 这个条件独立于 `now - lo.t > s`）。`army()` 每 0.8 秒跑一次（`every('army', 0.8)`），威胁质心 `tc` 只要有 1 格漂移，旧代码的 `pt` 就可能跟着变 1 格，等于每 0.8 秒都在重发 `AttackMove`。**这个机制性描述是成立的**，2 格网格取整能让质心必须累计漂移 ≥1 个网格单位（约 2 格）才会重新下达指令，理论上能把重发频率降低。
- **本局是否被日志证实**：**不能直接证实，只能间接印证**（原因见上面第 0 条——`log.json` 未导出，没有 order 级别的时间戳可用）。间接证据：commander_log/analyst_log 记录的现象——3:38–4:06 期间我方部队"从 12 单位/6150 打到 1 单位/180"且期间没有观察到明显的撤退/机动记录（analyst 4:27 报告"兵力骤降"而不是"部队已转移位置"），与"部队原地被磨、没有有效还击或走位"的描述一致，但这既可能是 `pt` 抖动导致指令被打断，也可能单纯是兵力劣势下的正常战损（尤其如果对手确实有指示 1 里说的隐藏火力）。**两个假设（threatValue 低估 + pt 抖动）很可能是同时生效、共同导致崩盘的**，本局数据不足以拆分各自贡献。
- **结论**：**明确标注为"待 match-007 验证"，不写成"已确认修复"**。本局全程用的是旧 runtime（`rt-d5b11898dd`），修复没有被热加载到运行中的页面（主会话判断热加载风险太高，属于正确的保守决策）。下一局如果同样出现"部队原地不动持续掉血"的现象，且新 runtime 已经生效，应重点关注这个现象是否明显减少；如果依然出现，说明还有其他因素（比如指示 1 的伤害低估）是主因，需要继续排查。

## 6（追加）矿车常驻护卫（用户追加要求 3）

- 代码审计结论：现在对矿车的保护只有 `army()` 里的 `hurtMiners`（血量 <95% 且附近有敌军）→`exposedMiners`（撤回基地）两段**被动反应式**逻辑，矿车必须先挨打、且血条掉破 5% 才会被处理，**没有任何常驻护卫/巡逻机制**。
- **本局及既往几局证据核查**：手头数据（commander_log/analyst_log，全视野数据本局已丢失见第 0 条）**没有找到"矿车在没有任何先兆下被一击秒杀"的直接记录**——match-006 的矿厂损失（8:55/9:00）记录的是建筑被拆，不是矿车行进途中被偷袭；`opponents/ai-easy.md` 里 match-003/004 有"专打落单矿车、引诱防守部队离开防御塔"的记录，但那是靠 HTK 之类持续开火而不是一击致命，现有的 `hurtMiners` 反应逻辑理论上来得及应对。真正的风险点是 GHOST2 的 Sapper（2500 伤害/一发，任何建筑一击必杀）和疑似同类机制的 SREF——如果这类单位对矿车使用同样的一击必杀逻辑，被动的"血量<95%再撤"阈值会完全失效，但**本局没有直接证据证明这已经发生过**。
- **结论**：这是一个**风险预防性提案**，不是从本局战损直接推导出的确认规律。已写成战术库 **T-026**（设计提案，候选），含具体实现思路（按 `minersPerRefinery` 预留 1–2 个常驻护卫单位驻扎在 `M.oreTiles` 附近，检测到矿区出现敌方单位就主动迎击，不等 `hurtMiners` 触发；建议加一个默认关闭的 `minerEscort` plan 字段，由指挥官在确认对手有"专打矿车"倾向时手动开启，避免无谓分兵）。建议主会话评估是否实现；如果实现后连续几局都没有观测到"矿车事前被单杀"的实际案例，应该在后续复盘里降级/废弃这条，避免不必要的兵力分散。
