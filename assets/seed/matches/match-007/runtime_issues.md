# match-007 执行层问题（runtime rt-07c4d2b657）

用户赛后明确提出的核心疑问："依然给坐下的步兵摧毁大部分"——本文件按用户要求逐条核实 match-006 之后加的修复是否真的解决了问题，如实报告，不美化结论。

## #1（本局最重要）T-022 的 threatValue 加权算出来了，但从未被用来决定"打不打得过"——这不是"权重不够"，是"权重没接上任何决策"
- **现象**：`army()` 里 `dmgWeight`（runtime.js:405）对持续静止 ≥2 个 intel 周期的步兵单位按 1.6 倍计入 `threatValue`（runtime.js:406）。代码审计确认 `threatValue` 在整个函数里只被用在两处：
  1. runtime.js:440，`log('alarm', ...)` 的展示文本（只影响可读性，不影响任何行为）；
  2. runtime.js:442，`recallAll = threatValue > myValue * 0.25`，只决定"是否把正在深入敌境的进攻部队召回防守"——这段逻辑只在 `M.attack` 不为空（我方正在主动进攻）时才有意义。
  防守分支本身（runtime.js:430-446，`if (threats.length) {...}`）**无条件**把 `defenders` attack-move 到迎击点 `pt`，不检查加权后的战力对比，也没有任何"打不过就撤"的判断——`retreatRatio`（runtime.js:465）只在 `P.stance === 'attack'` 分支生效，防守分支完全没有对应的退出条件。
- **本局证据**：3:16-3:41，我方 3 MTNK + 5 E1（价值 3150）在迎击点 (78,112-115) 原地接战 25 秒，被磨到 0，只换回 5 E1（900），交换比约 1:3.5，外加 1 座矿厂（GAREFN）被打掉。用 `snapshots.json`（10 秒粒度）核实：我方部队坐标在这 25 秒里是 (78,114)→(78,115)→(78,115)→(78,114)→(78,114)，**没有抖动/漂移**——2 格网格取整那个修复（T-011 附注）确实生效了，但即便位置完全稳定，部队还是被磨光，因为压根没有代码在"打不过就撤"这件事上做判断。
- **影响**：直接导致这场仗从"可以及时止损"变成"打到全灭"，是本局最大的一次战力损耗（3150 价值），间接导致后续 JUMPJET 来袭时我方已无兵可用。
- **建议的代码改法**（`army()` 函数，runtime.js:357 起）：
  1. 仿照 `M.attack.value` 的做法，给防守交战也建一个"本次交战开始时投入的部队价值"基线（比如 `M.defend = {value: myValue, t: now}`，在 `M.alarm` 从 false 变 true 时记录），后续每 tick 比较当前投入部队价值和这个基线，跌破某个比例（可以复用 `retreatRatio` 或新增一个防守专用字段）就把部队撤到塔后或干脆撤回基地，而不是无限期原地对射。
  2. `dmgWeight` 的系数本身建议重新评估——1.6 只反映了 M60→M60E 的输出提升（实测 1.667），没有反映本局新发现的 `proneDamage` 机制（见 #2）。如果要保留单一标量，考虑分场景：我方主战单位是 AP 武器（MTNK/LTNK 等）时用更高的系数（≈3），是 SA/步兵为主时维持接近 1.6-2.4。
  3. 这两条目前都**不能**通过 `evolve.py promote` 的 plan 字段实现——`stationaryInfantry*` 之类的新字段会被 `plan_keys()` 的 unknown-field 校验直接拒绝（已现场验证：`DEFAULT_PLAN` 里没有这个键），必须先在 runtime.js 里加字段和逻辑，下一版 plan 才能引用它。

## #2 卧倒/部署步兵还有一层此前完全没记录过的减伤机制（proneDamage），且它只对我方（进攻方）不利
- **现象**：现场用 `window.__cmd.game.rules.getWarhead(name).proneDamage` 核实到：这是一个独立于装甲乘数表的第二重乘数，只在**目标**处于卧倒/部署状态时生效（伤害 = base × armor_mult × proneDamage，目标非 prone 时 proneDamage 视为 1）。已核实：AP=0.5、SA≈0.7、RifleBullet=1、SSA=0.5、SAMWH=1、PrismWarhead=1。
- **量化影响**：MTNK 的 105mm(AP) 打卧倒 E1（none 装甲）真实伤害 = 65×0.25(armor)×0.5(prone) = 8.125/发，DPS≈2.03（杀 1 个 125HP 卧倒 E1 要 61.6 秒），而不是只算装甲乘数时的 16.25/发、DPS≈4.06（30.8 秒）。**MTNK 对卧倒步兵的真实杀伤效率只有"看起来"的一半**，叠加对方输出提升 1.667 倍，综合交换比劣势约是面值估算的 3.3 倍。本局 3:16-3:41 那场仗里 3 辆 MTNK 阵亡、事件日志里没有一次由 MTNK 直接确认的击杀（5 个 E1 击杀更可能来自我方 E1 的 SA 火力或塔火），和这个比例吻合。
- **建议**：`knowledge/units.json` 已经把这个机制记录进 `warhead_verses._prone_damage_note`，供后续对局参考；如果要让执行层自动利用这个信息（比如 #1 提议的加权系数按"我方主战单位是什么武器"动态调整），需要 runtime.js 在计算 dmgWeight 时读取我方 `units` 里的武器 warhead 类型，目前没有这个逻辑。

## #3 防空建筑（NASAM）实质上被资金饥饿保护永久卡死，`airSeen` 反射形同虚设
- **现象**：`wantDefenses` 在 `M.airSeen` 触发后会把 `want.aaDef` 提到 1（runtime.js:172），但 Armory 队列真正排产的门槛是 `(pd.credits > 700 && pd.credits >= c * 0.5) || (M.alarm && c <= 700)`（runtime.js:264）。NASAM 现场核实 `cost: 1000`——**恒定超过 700，永远无法走 `M.alarm && c<=700` 这条资金饥饿保护的快速通道**，只能等 `credits>700 且 >=500` 的正常门槛。本局资金从 ~1:11 起就反复触发"资金不足"保护（多达 8 次 reflex 提示），3:50 `airSeen` 正确触发之后我方 4 次赛后快照（3:52/4:39/5:14/5:27）的 `buildings` 里从未出现过 NASAM，0 次排产记录。
- **影响**：7 架 JUMPJET 在我方基地内部驻留超过 90 秒，全程零空中拦截，是本局崩盘的直接触发点。
- **建议**：已在候选方案里给出一个不需要改代码的缓解办法（v007 candidate：把 `aaDef:1` 写进初始 `defenses`，让它在开局资金充裕〔前 60-90 秒〕时就被排上，不用等 `airSeen` 触发）。但这只能缓解"排队晚"，不能解决"资金紧张时排不上"的根本问题——如果本局这种从 1:11 就开始缺钱的经济状态复现，即使把 aaDef 写进初始 plan，也可能在真正需要之前排不完。更彻底的代码改法：给 `aaDef` 单独开一条不受 700 门槛限制的资金保护规则（类似矿车"最多 2/矿厂不受饥饿保护限制"的例外，runtime.js:275-277），或者干脆把 NASAM 排产的优先级设为高于普通载具/步兵排产。

## #4 JUMPJET 可以完全绕开地面拴绳/迎击点体系，直接降落在基地纵深长期驻扎
- **现象**：`leashRadius`/`defenseDistance`/迎击点这套机制的设计前提是"敌方沿地面路径接近"，`threats`/`outside` 的判定本质是"离建筑多近+离锚定塔多近"。JUMPJET 作为飞行单位不需要沿地面路径移动，可以直接出现在基地纵深（本局：(71-73,116-120)，distToMyBase 1-3），且它是"驻扎型"用法，不是打一下就走。全局事件日志里没有一次针对 JUMPJET 群的专门迎击/集火记录，只有零散的 kill/loss。
- **影响**：这是本局崩盘的直接机制——即使 #3 的资金问题被解决、NASAM 造出来了，现有代码里也没有一条专门反射在"发现敌方飞行单位持续停留在基地半径内 N 秒"时做出响应（比如强制优先造 AA、集中火力打它们），完全依赖已有的 `threats`/迎击点逻辑能不能顺带覆盖到——本局的证据显示覆盖不到。
- **建议**：在 `siege()` 或 `army()` 里新增一条独立反射：检测到敌方飞行单位（`isAir(o)`，已有此函数）持续 N 秒（建议 15-20 秒）停留在 `defenseDistance` 半径内，且当前没有可用地面部队时，无视资金饥饿保护、强制优先造 NASAM/aaVehicle，这应该是比经济保护更高优先级的"基地即将被空拆"警报。

## #5（次要）alarm 日志只在交战开始时打印一次快照式的 threatValue，不会随着交战推进/敌方增援更新，容易误导实时角色对"敌方投入规模"的判断
- **现象**：`M.alarm` 是一个开关（runtime.js:440），"基地/矿车受威胁"日志只在它从 false 变 true 的瞬间打印一次 `threatValue`。如果交战持续了 25 秒且敌方期间不断有新单位加入（本局怀疑是这种情况：3:16 alarm 只报 1 个 E1/180，但整场仗我方最终杀了 5 个 E1、损失远超"1 个 E1"能造成的量级），后续的日志读者（commander/analyst/复盘）都容易低估真实交战规模。本局 commander 就在赛中日志里明确记录了这个困惑（"当时全程可见敌方 field 只报 2 E1，与我方损失的量级对不上"）。
- **建议**：`M.alarm` 保持 true 期间，每隔 N 秒（比如 10 秒）重新打印一次当前 `threatValue`/`threats` 构成，而不是只在触发瞬间打印一次；或者干脆把"威胁解除"时的总损耗（我方在这场交战里实际损失了什么）也打进日志，方便事后复盘不需要再去反查 loss/kill 序列重建。

## #6 `siegeAutoAttackUnits`（默认 8）只数单位数量，不检查装甲构成或敌情，容易在开局把纯步兵送出去
- **现象**：`siege()` 的判定是 `armyUnits.length >= P.siegeAutoAttackUnits && 10 秒没看到敌方部队`（runtime.js:508-511），不检查这些单位是不是清一色步兵、也不检查敌方主力是否正在逼近。本局 1:07 触发时我方仅有的 8 个单位是清一色 E1（MTNK 还在建 79%），被自动派去攻击敌方基地，同时敌方 5 E1 正在逼近我方基地——方向明显错误。指挥官 1:19 手动纠正（`siegeAutoAttackUnits`→14），纠正生效前已经产生约 0.6:1 的不利交换。
- **建议**：v007 候选方案已经把默认值从 8 上调到 14（缓解措施，plan 字段可以直接做）。更彻底的代码改法（供后续评估）：给这条反射加一个前置条件——至少含 1 个载具，或者敌方 `armyHist` 显示的 field 部队没有处于 "approaching" 状态。
