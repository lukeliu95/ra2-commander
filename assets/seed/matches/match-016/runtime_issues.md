## #1 `rearmIdleMiners()` 没有"矿区仍被占领"的门槛，把矿车送回交火区（本局最贵的一条）

**现象（时间 + 数据）**

- 4:09–4:30 的 **26 秒**内我方连丢 **4 辆 CMIN = 5600**（占全局损失 27800 的 20.1%），其中 4:09/4:14 早于敌方第二波（4:20–4:21，7050）被记录到门口的时间。此后**全局再未产出任何收入**：37 张全视野快照里我方 `CMIN` 计数从 **t=272（4:32）起一直为 0**（t=262/4:22 时还剩 1 辆，即 4:30 阵亡的那辆），直到 6:02 判负。
- 4:21 触发 `[reflex] 发现 1 辆矿车完全闲置（无指令无任务），用原生 gather 重新武装（资金 0）`（`install.js:893`，`rearmIdleMiners()`）——**9 秒后（4:30）该辆 CMIN 阵亡**。
- 我方最近的矿格在 **(84,122)/(85,120)/(86,120)**，距我方基地 (71,118) **13.6–15.1 格**（战后 `getAllTilesResourceData()` 实测，全图 367 个矿格）；而敌方第二波 4:21 的质心在 **(83,112)**、4:31 在 **(82,111)**——**距我方矿区只有 8.2–10 格**。矿区 1:05 的工厂与 3 座 GAREFN 也都在这个方向（GAREFN 放置 @75,116 / @78,120，`placementCenter` 朝最近矿格偏移 0.6，与最近矿格 (84,122) 的推算位置 (78.8,120.4) 吻合）。

**影响**：5 辆矿车里最后这 1 辆的 9 秒存活，决定了 4:22–6:02 的资金恒为 0。若是它活下来，`GAREFN 70%`/`ATESLA 95%`/`MTNK 42%` 三条冻结队列至少有一条可能收敛（见 #2）。**这是本局唯一一条"改一行就能改结局"的候选**。

**推测原因（代码级）**

- 撤退反射本身**已经**有防重复投喂的保护：`install.js:468–476` 计算 `patchHot = S.hostile.some(o => ... d2(xy(o), spot) < 12*12)`，命中就 `continue` 并打日志 `矿区 @x,y 仍有敌军，暂不重派矿车`。
- 但**看门狗 `rearmIdleMiners(S)`（`install.js:889–897`）只判断"该单位无指令且无任务"，没有任何敌情/矿区检查**，直接 `harvesterTrait.queueAutoGatherAfterOwnershipSettles(m, game)`。它与 `patchHot` 是两条独立代码路径，后者拦不住前者。
- 注意本局**没有**出现 `矿区 … 仍有敌军，暂不重派矿车` 这条日志（0 条），也没有 `矿车…重新派回矿区`（0 条）——因为 4:04/4:16/4:29 三次撤退后矿车都没活到"伤势恢复或 40 秒超时"的判定点，看门狗先一步把它们重新武装了。

**建议改法**

1. 把 `install.js:468–476` 的 `patchHot` 抽成一个纯函数 `patchHot(spot)`，在 `rearmIdleMiners()` 里对每个待武装矿车取它的最近矿格（`M.oreTiles`，同上）后先判 `patchHot`，命中就跳过并 `every('rearmHot', 15)` 打一条日志。
2. 顺带把"撤离目标"从 `baseCenter()`（建造厂）改成"离威胁最远的已探明矿格或基地另一侧"，或至少在 `patchHot` 持续期间让矿车留在基地（目前的行为等于 0 收入，但不是立即死亡）。**本局的数据不支持"撤回路径穿过交战区"这个说法**（见 debrief §3 的几何核对），所以这条只提高鲁棒性，不改变本局归因。

## #2 单槽 Armory 被一个"付不起的 ≥1500 项"占死 118 秒，期间**任何**防御补建在结构上都不可能

**现象（时间 + 数据）**

- 3:06 `放置 GAAIRC @72,121` → **3:07 同时** `排产 GAREFN（资金 617）`（Structures）与 `排产防御 ATESLA（1500，资金 617，敌方逼近，绕过资金门槛）`（Armory）。两条日志相隔 1 个 seq（112/113/114），即**在同一瞬间把两个 ≥1500 的项塞进两条队列，账上只有 617**。
- 指挥官的现场采样：**3:55 / 4:21 / 4:46 / 5:11 四次都停在 `Armory:ATESLA 95%`**，同期资金长期为 0（37 张快照里 5:00 之后只有 1 张非 0）。**ATESLA 整局从未进入 `me.buildings`、0 条 `放置防御 ATESLA`。**
- 4:35 / 4:44 / 4:45 / 5:03 / 5:05 我方依次丢掉 GAPILL#1/#2、NASAM#1、NASAM#2、GAPILL#3 → 到 5:05 时 `baseDef 3/3` 与 `aaDef 2/2` **双双不满足**，而 Armory 队列里**没有任何补建尝试**——因为 `production()` 的防御排产**只有一条入口**：`install.js:279` 的 `else if (dq.status === ST.Idle && dq.currentSize === 0)`。只要队列里挂着任何一项，这条分支整段不会执行。
- 该状态一直持续到 ATESLA 消失（见 #3），**5:22 才排产了全局唯一一座补建防御 NASAM（资金 1416）**，而它到判负也没落地。

**影响**：这是 match-014 `break` 锁死 bug 的**同类形态在修复后重新出现**——014 是"选错了角色"，本局是"选对了角色但付不起、于是谁也排不上"。我方防御建筑从 3:32 的 **13 座**掉到 5:32 的 **5 座**，全程**零次**补建尝试。

**推测原因（代码级）**

- 放行门槛：`install.js:305` `const strongUrgent = role === 'strongDef' && groundNear && pd.credits >= c * 0.3;` → ATESLA 只要 `groundNear` 且资金 ≥ **450** 就能进队。资金 617 满足，于是它进了队列；**而"进队"与"造得完"之间没有任何联系**。
- 现有的资金饥饿保护 `install.js:229–232` 只做一件事：把**步兵/载具**队列暂停（`starved`）。它**从不阻止建筑/防御排产**，也从不检查"Armory 队列里已经有一个付不起的 ≥1000 项"。
- 结果：3:07 之后我方是"三方分零收入"——`Structures:GAREFN(2000) 70%` + `Armory:ATESLA(1500) 95%` + `Vehicles:MTNK 42%/CMIN 0%`，合计约 **2825 已沉没、0 产出**。

**结论：值得修，而且是本局第 2 优先。** 它是 T-013 的近亲（"不看资金就占住唯一队列"），但比 T-013 更隐蔽：T-013 是 buildOrder 项，这一条是**紧急通道主动放行**的项。**注意：本局不能证明"改成不排队就能换来一座塔"**（见 debrief §2 的反事实核算），能证明的是：**在 4:35–5:22 的 47 秒里，我方连"尝试补一座 500 的 GAPILL"这个动作都不存在，因为执行层没有第二条入口。**

**建议改法**

1. 把 `expensiveBusy` 的语义从"只暂停步兵/载具"扩展到**防御排产**：`install.js:299` 的循环里，若 `M.starved` 且队列里已有一个未完成的 ≥1000 项，**拒绝** `strongUrgent` 通道放行（资金 617 时 ATESLA 就不会进队，Armory 槽留空）。判据可直接复用 `M.starved`（本局 1:17/2:43/3:08/3:27/4:21/5:25 六次进入该状态，覆盖了整个 3:07–5:22）。
2. 更彻底的一条：给 `install.js:279` 的分支加一个"队列被一个付不起的项卡住 ≥45 秒"的出口（见 #3 的停滞检测），让 500 的 baseDef 能在同一威胁下插队。

## #3 引擎侧的队列取消对 runtime **完全不可见**：ATESLA 消失 + ~1400 退款没有任何日志

**现象（时间 + 数据）**

- ATESLA 在 5:11 的采样里还在（95%），5:36 的采样里已经换成 `Armory:NASAM 36%` → **它在 5:11–5:36 之间离开了队列，且从未 `放置`**。
- 同期资金出现一笔**无法用采矿解释**的增加：`排产防御 NASAM（1000，资金 1416）`。**我方从 t=272（4:32）起 `CMIN` 计数恒为 0**（t=252/4:12 是 3 辆、t=262/4:22 是 1 辆，t=272/4:32 起为 0，此后 10 张快照无一例外）→ 没有任何收入来源能让资金涨到 1416。
- 该笔钱**只能来自引擎对已取消项的退款**，且**只能是 ATESLA 那笔**：同一时刻 Structures 队列里仍挂着 `GAREFN 70%`——若是 GAREFN 被取消，队列会立刻变空，而 `install.js:243–252` 的兜底（`counts['GAREFN']=0 < targetRefineries=3 && av.has('GAREFN')`）会**马上**排产一座新的 GAREFN 并打出 `排产 GAREFN` 日志；3:07 之后**全局没有任何 Structures 排产日志**（下一条是 5:22 的防御 NASAM）。
- 取消的**触发条件**由规则表可读：`game.rules.getObject('ATESLA',2).prerequisite = ['RADAR','GACNST']`，而 `R('radar')` 在本局解析为 **GAAIRC**（3:06 放置 @72,121，**5:23 被拆**）；同一条证据链还能解释 5:22 那一座为什么是 **NASAM 而不是 ATESLA**——`install.js:302` 的 `!av.has(name)` 会跳过 strongDef，`DEF_PRIORITY` 于是落到 `aaDef`，而 NASAM（1000）在资金 1416 下通过 `credits > 700 && credits >= 500`。

**影响**：本条**不直接掉血**，但它是本局"证据链断掉"的根源——指挥官和分析员为此各写了一套互相矛盾的归因（"资金饥饿冻结" vs "放置环节静默失败"），耗时耗力，**而真相（前置建筑被拆 → 引擎取消 + 退款）两边都没写出来**，因为 runtime 完全没有这条信息。

**建议改法**

1. 在 `production()` 里维护一个"我方主动入队的项"台账（`M.queued = Map(name → {t, progress})`），每 tick 与 `queue(t).getAll()` 对账：**项消失而我方没有调用 `placeBuilding`、也没有调用 `unqueueFromProduction`** → `log('warn', '排产项被引擎取消：NA（进度 x%，退款约 y）')`。
2. `M.pendingPlace` 已经是一个可用的旁证：它每成功放置一次才 +0.8 秒（`install.js:238/278`），本局从 3:06 的 GAAIRC 之后**一直停在 187.63（= 3:07.6）到终局**，这本身就能证明"3:07 之后我方一次放置都没成功过"。建议把它一并写进上面那条 warn。

## #5 `warn 防线外有敌军在打我方建筑…` 的文案已经把规模写在里面了，但缺"危险等级"

**现象（已核对，纠正两个角色的口径）**：本局 `warn` 共 **9 条**，其中**只有 7 条**是这条拴绳 warn（0:53 / 1:27 / 2:00 / 2:32 / 2:47 / 3:02 / **4:20**），另 2 条是 `侦察犬已连续阵亡 3 次`（2:04）与 `敌方重型单位正在基地附近逗留`（2:50）。**指挥官日志里"整段出现 5 次 / 13 次"、分析员表里"9 条"都不准，以 7 条为准。**

- 前 6 条 comp 全是**单兵**（ADOG×1 或 E1×1，价值 200–288），这 6 个时间窗内**我方建筑损失为 0**。
- 第 7 条（4:20）comp = `{"JUMPJET":6,"MTNK":3}` = 7050，**15 秒后（4:35）丢第一座 GAPILL**，此后 48 秒丢 9 座。
- **但"单兵和混编波发的同一条文案"这个说法不准确**：`install.js:524` 的模板是 `防线外有敌军在打我方建筑：${JSON.stringify(tally(outside.map(o => o.name)))}` —— **composition 本来就在同一行里**。缺的不是信息，是**等级**。

**影响**：低。本局实时角色 7/7 都正确判读（4:20 那条被分析员在 4:57 引为"全局最早的转折信号"）。这是可用性改进，不是胜负杠杆。

**建议改法**：把威胁价值一起打出来并按档位分级，例如 `< 1000 → info`、`1000–3000 → warn`、`> 3000 → warn(<urgent>)`，并把 `every('outsideLeash', 15)` 按档位分别节流。**注意：绝不能按阈值直接抑制**——4:20 那条正是最早的真信号。

## #6 新增的部署反射：两处需要复核（主会话 22:02 刚加的代码，本局未运行）
