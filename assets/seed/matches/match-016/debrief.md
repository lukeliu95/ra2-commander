## 2. ATESLA 之争的裁定 + "30% 门槛值不值得修"

### 2.1 裁定：**指挥官的机制判断对（资金饥饿冻结），但其归因不完整；情报员的"放置环节静默失败"不成立。真相是第三种：前置建筑被拆 → 引擎取消 + 退款。**

**四层证据，前两层是代码级的（不依赖资金曲线）：**

1. **放置分支根本没被进入。** `install.js:275` 是 `if (dq.status === ST.Ready && sec() >= M.pendingPlace)` —— 放置只在队列项**造完（Ready）**时才发生。而 ATESLA 全程停在 **45%→95%**，从未到 Ready。**"静默失败"必须表现为进度到 100%/Ready 而没落地，本局的形态完全不符。**
2. **旁证：`M.pendingPlace` 从 3:07 冰封到终局。** 该变量每成功放置一次才前进 `sec()+0.8`（`install.js:238/278`）。赛后读页面：`pendingPlace = 187.63` = **3:07.6**，正对应 3:06.8 放置 GAAIRC 那次。**整个后 2:54 它一次都没动过** → 我方**一次 `placeBuilding` 都没调用**，`findSpot()` 也没被调用过（否则会打 `找不到 X 的位置` warn，本局 0 条）。**"放置环节失败"在这一层就已经被排除。**
3. **冻结的成因是资金：** 指挥官 3:55/4:21/4:46/5:11 四次采样都是 `Armory:ATESLA 95%`，同期资金恒为 0；同一时刻 `Structures:GAREFN 70%`、`Vehicles:MTNK 42%` 一起冻结。**runtime 自己的注释早就记录过同型机制**（`install.js:227`："Four queues splitting zero income never finish the expensive one (match-004: TESLA sat at 66% for 3.5 min)"）。**进度条冻结 = 资金饥饿的签名。**
4. **它的消失（5:11–5:36 之间）是引擎取消 + 退款，不是 reconcile，也不是放置：**
   - ATESLA 的前置建筑由规则表可读：`getObject('ATESLA',2).prerequisite = ['RADAR','GACNST']`，而 `R('radar')` 在本局解析为 **GAAIRC**（3:06 放置，**5:23 被拆**），GACNST 5:36 被拆。
   - **同一瞬间的另一条证据链**：全局唯一一次补建防御是 `排产防御 NASAM（1000，资金 1416）`。**注意它排的是 NASAM 而不是 ATESLA**——`install.js:302` 的 `!av.has(name)` 会跳过 strongDef，`DEF_PRIORITY` 于是落到 aaDef。**这说明那一刻 `av.has('ATESLA')` 已经为 false，即 RADAR 已经没了**（日志里的 `loss GAAIRC` 比实际摧毁晚 1–2 秒）。
   - **那 1416 块钱只能是退款**：我方从 **t=272（4:32）起 `CMIN` 计数在快照里恒为 0**（t=252/4:12 是 3 辆、t=262/4:22 是 1 辆、此后 10 张连续快照全是 0），没有任何收入来源。而且**退的只能是 ATESLA**——同一时刻 Structures 队列仍挂着 GAREFN（若是 GAREFN 被取消，`install.js:250` 的兜底会立刻重排一座并打日志；3:07 之后全局**没有任何 Structures 排产日志**）。
   - **`reconcileQueues` 不可能是凶手**：`need[Q.Armory]` 用的是 `sumFor(wantDefenses(P,av), 'ATESLA')`，而 `wantDefenses` 对 strongDef **不检查 `av`**（`install.js:182–186` 只对 aaDef 特判），所以 `want.strongDef = 2` 恒真、`0 < 2` 恒真 → **reconcile 永远不会取消它**。

**裁定**：3:07–5:11 是**资金饥饿冻结**（指挥官对）；5:11–5:36 是**引擎因前置建筑（RADAR/GAAIRC）被拆而取消并退款**（**两个角色都没写出来**）；情报员的"放置环节静默失败" **不成立**（代码级排除）。**整局 ATESLA 零输出，我方对 MTNK 的唯一高效火力（PrismShot 120 伤、对 heavy 1.0、射程 8、杀一辆 300HP 灰熊 3 发）全程缺席。**

## 3. 经济断供的机制（4:09–4:30 连丢 4 辆 CMIN = 5600）：**指挥官"撤回路径穿过交战区"的说法不成立**

**事实链（逐条核 `log.json`）**：

| 时间 | 事件 |
|---|---|
| 4:04 | `矿车在防线外被打：撤回基地（1 辆）` |

**三条几何/口径核对：**

1. **"每条死亡都紧跟在 1–5 秒前的撤回之后"不成立**：只有 **3 条**撤回日志（4:04/4:16/4:29）对 **4 条**死亡——**4:14 那次死在前一条撤回（4:16）之前 2 秒**，不可能由它引起。而且撤回日志被 `every('minerHome', 10)` 限流（`install.js:522`），**日志里的 3 条本来就少于实际下达的撤回指令数**，所以"1:1 配对"从口径上就不成立。指挥官的排序还把它自己写成了"4:16 撤回 → 4:14 死"（倒因为果）。
2. **撤退方向是对的，不是"穿过交战区"**：`install.js:521` 的撤退目标是 `baseCenter()` = **建造厂 (71,118)**。我方最近的矿格在 **(84,122)/(85,120)/(86,120)**（战后实访 `getAllTilesResourceData()`，距基地 13.6–15.1 格；GAREFN 放置 @75,116/@78,120 与"朝最近矿格偏移 0.6"的推算位置 (78.8,120.4) 吻合）。**从矿区回基地是朝西南走，而敌方第二波 4:21 在 (83,112)、4:31 在 (82,111)——在矿区的西北/北面。撤退路线与敌军的垂距约 9 格**，而 MTNK 射程 5、FV 射程 6 → **撤退路径本身没有进入敌军火力圈**。
3. **真正的机制是"矿区本身处在敌军前进区"**：我方矿区 **(84,122) 距敌军 4:21 的驻地 (83,112) 只有 8.2–10 格**，而矿区距我方基地 13.6 格——**在敌方第二波从东北压进来时，矿区正好在它进门时路过/停驻的一侧**（它 4:31–5:03 一直停在 (79–82,111–112)，5:13 才推进到 (77,117)）。**矿车是在被争夺的矿区里被打死的，不是在撤退路上。**

**结论：这是局势必然（矿区离基地 13.6 格、且在敌方进门的必经地带）+ 一条真实的执行层缺陷，但不是"撤回目标点没避开威胁"。**真实的执行层缺陷是 **`rearmIdleMiners()` 缺少 `patchHot` 门槛**（`install.js:889–897` 与 `:468–476` 是两条独立路径）：4:21 那辆被"重新武装"的矿车 9 秒后阵亡，而 12 格的 `patchHot` 保护**只对撤退重派生效、对看门狗完全无效**。**这是我给主会话的第 1 优先修复项**（`runtime_issues.md` #1）。

**顺带纠正一个口径**：指挥官总结说"CMIN 峰值只有 2 辆"，**37 张全视野快照显示峰值是 4 辆**（t=212–242，即 3:32–4:02），补矿车事件 3 次（0:56 1/2、2:43 2/4、4:09 3/4）。4 辆 = `min(maxMiners 12, refs 2 × minersPerRefinery 2)`，**说明本局的经济其实正好卡在"2 矿厂 × 2 矿车"的设计值上，是"第 3 座矿厂从 3:07 排到判负都没落地"才让上限停在 4。**

### 已落地

**A. 新增"防守态步兵部署"反射（用户直接提出的线索，match-003 的 `runtime_issues` 就提过，一直没实现）**

`army()` 里加了一段：防守姿态、且当前没有敌军在打我方的时刻，把**已经停在集结点 6 格内**的步兵用 `ORD.DeploySelected` 坐下来。选"已经停在集结点"这一批是有原因的——正好是部队集结反射不管的那批（它只处理离集结点 >6 格的单位），两条反射不会互相打架。

两道保险：
1. **部署是开关**，所以用一个位置账本记住每个单位坐下时站在哪一格，没挪动过的绝不再碰它（否则会把它们一次次叫起来）；这个账本还会自愈——单位被下令移动时引擎会自动让它站起来，坐标一变就重新具备部署资格。
2. **能不能部署由引擎字段决定**（`rules.deployer === true`），不看兵种名。**这一条是学习员在 `runtime_issues` #6 里抓出来的**：我第一版写成"名字等于 `R('inf')`"，而实测 `E1`（盟军步枪兵）是 `deployer/deployFire = true`、`E2`（苏军动员兵）**两个都是 false**——照第一版写，苏军局里会每个 tick 给每个动员兵发一条无效指令。已改，并把日志改成打印真实兵种构成。
   同时改掉了那句不准确的注释：守卫不是写在反射里的，而是**由调用点保证的**——`threats` 非空时上面的分支会 `return`，所以这段代码只在"没人打我们"时才到得了。

**B. `rearmIdleMiners()` 补上矿区敌军门槛（`runtime_issues` #1）**
