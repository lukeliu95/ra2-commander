## #1【最高优先】`finishing`（清场模式）会把新出厂单位自动加入攻势 → 持续添油送死

- **现象**：4:12 转攻后，新出厂的 MTNK 一辆一辆**单独**走 70 格到敌家门口逐个阵亡。4:12 发起时 15 单位/9540，到 5:04 掉到 5 单位/2610（27%），5:44 我方累计损 18 辆 MTNK。整局损 24 辆 MTNK ≈ 21600，其中大部分发生在 4:12–5:44 这一段。
- **代码位置**：`install.js:556`
  ```js
  for (const u of units) if (!A.ids.has(u.id) && (finishing || d2(xy(u), rally) < 100)) A.ids.add(u.id);
  ```
  `finishing` 为真时，**任何不在 `A.ids` 里的单位（含刚出厂的）都被立即纳入攻势**，绕过了"攒在 rally 点等够规模"的原有约束。
- **为什么是问题**：这与 match-012 的教训互为镜像。match-012 错在"打得动却因为掉到 35% 就整体撤回"（过度谨慎）；本局错在"该撤却在**持续**投入新单位"（过度添油）。**"用现有部队打完剩余目标"与"不断把新单位送进敌方静态火力"是两件事，`finishing` 把二者混为一谈。**
- **建议改法（按优先级）**：
  1. `finishing` 只对**进入该状态时已在场**的单位生效（记录进入时刻的 id 集合），新单位仍走"攒到 rally 点"的常规路径；
  2. 或者：新单位改为**攒够 N 个（建议 4–6）**再一起出发，而不是单个加入；
  3. 或者：敌方仍有 `isBaseDefense` 建筑时（本局它是 4 座 CAPILL），**不**把新单位自动加入攻势。

## #2【高】`finishing` 判据只看敌方野战价值，不看敌方静态防御

- **现象**：4:12 `敌方野战力量仅 0：进入清场模式`。**该判据本身工作正常**（v011 已从 match-012 的"field 严格为 0"改成 `enemyFieldValue < 1500`，见 `install.js:547-555`，本局确实激活了）。**问题在于"敌方没有野战部队"被等价成了"敌基地可以低成本拆掉"。**
- 本局它家里长期停着 **4 座 CAPILL**（古巴专属重碉堡，650 元/**HP 600**，比苏系防空塔硬）——`field < 1500` 完全无法反映这部分火力。我方的 300HP/900 元 MTNK 在它家门口被这些 600HP 碉堡群近距离换掉，交换比从出塔线前的 4.67:1 掉到全程 0.36:1。
- **建议改法**：
  1. 进入 `finishing` 时额外检查敌方 `isBaseDefense` 建筑数量；**≥3 座时不进入清场模式**（或进入但**不**把撤退下限降到 0.14）；
  2. 或者在 `[attack] 进入清场模式` 的日志里**显式带上敌方可重建/静态防御的数量**，让指挥层能立刻判断这次清场是不是"低阻力"的。
- **配套（指挥侧规则，非代码）**：转攻前若 `knownBuildings` 中没有侦察到敌基地 `isBaseDefense` 的坐标与数量，则不转攻。本局 4:12 转攻时 `knownBuildings` 里**没有任何 CAPILL**，代价 ≈ 19800（22 辆 MTNK），而一次侦察 < 200。

## #3【中】矿车看门狗 `rearmIdleMiners` 未覆盖"有指令但无任务"的矿车

- **现象**：本局 CMIN 从峰值 6 辆一路掉到 1 辆（累计损 7 辆 ≈ 9800）。**6:11 之后再未出现任何"重新派回矿区"/"发现 N 辆矿车完全闲置"日志**，而同期有多次"矿车在防线外被打：撤回基地"反射触发（5:03 / 5:42 / 7:43）。资金 6:16 之后恒为 0，直到终局只回到 465。
- **代码位置**：`install.js:767-776`
  ```js
  const idle = S.mine.filter(o => o.rules.harvester).filter(o => {
    const uo = o.unitOrderTrait;
    return uo && uo.orders.length === 0 && (uo.tasks || []).length === 0;
  });
  ```
  判据要求 `orders.length === 0 && tasks.length === 0`。**在"被反矿车火力反复打断、每次打断都收到一条新 Move/撤回指令"的局势下，矿车可能长期处于"有指令但没在挖矿（tasks 为空）"或"指令队列非空但已失效"的状态，落不进这个判据。** 本局后期正处在这种持续被骚扰的形态。
- **建议改法**：把判据放宽到"`tasks` 为空且 `harvestedAmount` 在最近 N 秒内无增长"，不论 `orders` 是否非空；命中后用原生 `queueAutoGatherAfterOwnershipSettles` 重新武装（与现有修复一致）。
- **注**：本局 `minerEscort: 1` 全程开启，**未能阻止矿车被反矿车火力逐个点掉**（这与 T-026 的既有结论一致：护卫站在矿厂旁拦不到在野矿区打矿车的人）。本局**不构成对 `minerEscort` 的正面或反面证据**，因为无法区分"护卫存在但无效"与"护卫根本没到位"。

## #4【最高优先，与本节"附"栏第 4 条的结论相反】反击反射在**攻城期间**会把大部队从目标上拽走，且拽去的大多是不影响判负的建筑

- **现象（逐条重算，不是估算）**：全程 `反击：` 共 **18 次**（commander 记的是 13 次，漏计了 5 次）。其中 **7 次发生在 4:12–5:20 的攻城窗口内**：4:21（1 个单位→CAPILL）、4:29（2→CAPOWR）、**4:37（7 个单位→CAPOWR @76,118）**、4:45（6→PLA）、**4:53（6→CAREFN @75,123）**、5:07（1→PLA）、5:15（1→CARADR）。**合计 24 个单位次，其中 17 个单位次的目标是建筑，而这 5 类目标（CAPILL/CAPOWR×2/CAREFN/CARADR）没有一个在判负集合里**（判负集合 = 建造厂+兵营+战车工厂+空指部，见"附"栏第 6 条）。
- **为什么是问题**：`siege()` 刚刚用 `ORD.Attack` 把全组点在 CACNST（rank 0，唯一不可重建的目标）上，反击反射（`install.js:738-762`）就在 1–16 秒后用另一个 key 重新下 `ORD.Attack` 覆盖它。**最严重的一次是 4:37：11 个单位里有 7 个被拉去打一座 CAPOWR**，而 CACNST 从 4:12 到 5:14 一次都没被击破（同窗口我方拿到的唯一战果是 CARADR 4:33 和 CAPOWR 4:48，两座都与判负无关）。
- **影响**：这是"68 秒攻城对三类生产建筑零击破"的直接执行层原因之一；与 #1（自动添油）、#2（清场判据不看静态防御）、以及 60% 阻挡容忍度（`tol = M.finishing ? 0.6 : 0.25`）叠加。
- **建议改法**：
  1. 反击反射的候选目标按 `siegeRank()` 过滤：**stance === 'attack' 且 `M.attack` 存在时，只对 rank ≤ 1 的敌方目标（或正在攻击我方单位的敌方单位）触发**，非判负建筑（防御塔/电厂/矿厂/雷达）不参与；
  2. 或者把反击规模限制在"离受害单位最近的 1–2 个单位"，而不是 `RETALIATE_SQUAD_R = 14` 半径内的全部单位（本局 4:37 的 7 个、4:53 的 6 个都是这样凑出来的）；
  3. 攻城期的 `ORD.Attack` 应带一个更长的"不可被打断窗口"（现在的 `M.siegeHit` 只节流 6 秒，反击反射另有自己的 `M.retaliating` key，两者互不感知）。

## #5【高】进攻分支的撤退判据分母被"增援"稀释：`A.value` 固定、`gv` 被 `install.js:556` 持续补充

- **现象**：4:12 发起时 15 单位/9540，`retreatFloor = min(0.14, 0.14) = 0.14` → 下限 1336。`siege()` 日志里的 `gv` 实测最低 **2610（5:06，27.4%）**，`log` 里 **0 条 `进攻部队只剩 X%`** —— 自动撤退一次都没触发。而**按 loss 逐条重算，4:12 那 15 个单位（12 MTNK + 3 E1）到 5:00 已经 100% 阵亡**（4:27/4:29/4:33/4:35/4:38/4:42/4:45/4:47/4:50×2/4:53/4:54×2/4:56/4:59 = 15 辆 MTNK，加 5:00 前的 3 个 E1）；5:06 读到的 2610 **正好等于 3 辆新 MTNK + 2 E1（3×750+2×180）**，全部是 finishing 自动加入的替补。
- **为什么是问题**：分子的口径（"当前所有在 `A.ids` 里的活单位"）和分母的口径（"发起那一刻的编队"）不一致，于是**同一个 `retreatRatio`，在 finishing 自动添油开启时会被系统性抬高**：4:56 时按原始编队算已经掉到 1110（11.6%，连 0.14 都该触发），按现口径读出来却还在 27% 上下。这解释了为什么 0.35 在 match-012"太早"（那局 finishing 没激活，分母没有被稀释）而 0.14 在 match-013"永不触发"。
- **建议改法**（三选一或叠加，都需要 runtime.js）：
  1. **锁定编队**：`M.attack` 增加 `launchIds`，撤退判据的 `gv` 只统计 `launchIds` 里仍存活的单位，`install.js:556` 加入的新单位不参与该判据；
  2. **改成相对判据**：`gv < (near 单位价值 + 交战半径内敌方 isBaseDefense 建筑按有效 HP 折算的价值) × K`（K=2–3），让判据看得见"对面还有没有东西"；
  3. **加绝对损失速率**：最近 15 秒损失价值 > 当前集团价值的 25% 就撤。
- **v012 的临时处置**：plan 层把 `retreatRatio` 回退到 0.35（0.14 在本局等于关闭机制）。**注意：0.35 只把触发点提前到 4:54（早 26 秒），救不回整场——真正的修复在代码。**

## #6【中】矿车"撤回基地"后的复工链路本局 0 次走通：4 次撤回的矿车全部在 2–5 秒内被杀

- **现象**：`矿车在防线外被打：撤回基地` 4 次（5:03 / 5:42 / 5:52 / 7:43，各 1 辆），而 `重新派回矿区` **0 次**、`发现 N 辆矿车完全闲置` **0 次**。逐条对齐：5:03 撤回 → 5:08 损失 1 CMIN（+5 秒）；5:42 → 5:44（+2 秒）；5:52 → 5:55（+3 秒）；7:43 → 7:45（+2 秒）。整局 7 辆 CMIN 全损。
- **为什么是问题**：`exposedMiners` 的触发条件是 `hp(m) < 0.95` **且** 25 格内有敌军——**它要求矿车先挨打**；而当攻击者是 LTNK（90 伤/发）或成组单位时，从"血条掉破 5%"到"死亡"只有 2–5 秒，`M.retreatedMiners` 的 40 秒等待逻辑（`safe` 判定要求 hp ≥ 0.9 且 25 格无敌军）根本没机会跑完。**所以本局"看门狗 0 次"不能读成"复工链路正常"，它只是没被检验。**
- **与 #3 的关系**：#3 说的是"判据覆盖不到有指令无任务的矿车"，本条是"矿车在这条链路发挥作用之前就已经死了"，两个缺口是独立的。
- **建议改法**：(a) 触发条件加"先验"分支——矿区/矿车 8 格内出现敌方**战斗**单位（不等挨打）就先把矿车撤到基地侧，或者给矿车配 T-026 的常驻护卫；(b) `safe` 的 40 秒上限对"矿车血量已经很低"的情况缩短（例如 hp < 0.5 时无条件结束等待、立即重武装）；(c) 把"撤回后又派回"的日志补上失败路径（本局完全看不到这条链路是否被尝试过）。
