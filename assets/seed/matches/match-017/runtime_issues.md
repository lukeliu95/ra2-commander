## #1（P0，已修 `afb4b83`）`SIDES.CA` 的防御角色名指向苏军建筑，`defenses` 整条通道静默空转 7 分 46 秒

**现象（时间 + 数据）**

- `plans/v014.json` 的 `defenses {baseDef:3, aaDef:2, strongDef:2}`，**从 0:00 到 9:58 一座都没产出**：全 66 张快照的我方 `buildings` 里 `CAPILL`/`MSAM`/`CTESLA` **计数恒为 0**。
- 执行层自己在 3:16 报 `建筑队列已空闲 57 秒`（4:16 报 118 秒），说明 Structures 槽当时是空的；3:17 与 5:45 还各报了一条 `敌方重型单位/飞行单位正在基地附近逗留：相应防御排产已绕过资金门槛`——**反射自称绕过了资金门槛，实际什么都没排出去**。

- 唯一暴露根因的日志来自另一条通道：指挥官 6:21 把 2 个 `baseDef` 写进 `buildOrder`（想借道显式通道），执行层 **7:22/8:22/9:22/10:45 四次**打出 `建造顺序里的 baseDef(NALASR) 已 60 秒不可造，被跳过`。**`buildOrder` 通道有这条 60 秒 skip warn，`defenses` 通道当时一条都没有**——这是两个实时角色花了 6 分 47 秒才定位到根因的直接原因。
- 修复后：9:15 `排产防御 CAPILL（650，资金 349）` → **9:58 `放置防御 CAPILL @129,86`**（全档案第 1 座 CA 静态防御）→ **10:06 被 3 辆 MGTK 拆掉，存活 8 秒**。

**影响（多大程度左右了胜负）**

**决定性。** 三条直接后果：

1. **CA 唯一能反 MGTK 的资产（CTESLA，射程 8 > MGTK 的 7）全程 0 座**；9:34–10:02 我方 31 单位/21290 被 3 辆 MGTK 磨到 1 单位/200（**该窗口逐条重算：我方损 18900 : 击杀 2400 = 0.13:1**；把窗口前推到 9:21 的整段交战是 25450 : 6450 = 0.25:1）。
2. **CA 的 MSAM（对空射程 12）0 座**，敌方 JUMPJET 3:39 首见、峰值 8 架，我方只能靠 BGGY（300HP/armor3）和陆军高射火力硬扛，BGGY 全局损失 17 辆。
3. **开局到 9:58 共 7 分 46 秒没有任何静态火力**，而敌方 1:09 就在我方来向摆了 GAPILL（1:09 一座 → 5:10 五座，全在 (71–74,109–111)）。

**推测原因（已在代码侧确认）**

`runtime.js` 的 `SIDES` 表里 CA 行的 `baseDef/aaDef/strongDef` 是从 NA 行复制的占位值 `NALASR/NAFLAK/ATESLA`。`production()` 的 Armory 分支做 `const name = R(role); if (!n || (counts[name]||0) >= n) continue; if (!av.has(name)) { ...; continue; }`——CA 造不了这三个，`av.has` 恒 false，于是**每 tick `continue` 且不写日志**。`wantDefenses()` 返回 `{...P.defenses}`，只要键存在就会被当成目标，落不进"目标不存在"的分支。

**建议的代码改法（采纳情况）**

- 已采纳：CA 行改为 `baseDef: 'CAPILL'`、`aaDef: 'MSAM'`、`strongDef: 'CTESLA'`，并在 `!av.has(name)` 分支加 60 秒节流 warn（`if (every('defUnavail:' + role, 60)) log('warn', ...)`）。三个名字都在本局用 `game.rules` 现场核实过：`CAPILL` 650/600HP/`Vulcan2` 50 伤/射程 5.5/前置 `[BARRACKS,CACNST]` techLevel 1；`MSAM` 1000/900HP/`RedEye3` 55 伤/基础射程 6 + `airRangeBonus` 6/前置 `[BARRACKS,CACNST]` techLevel 5；`CTESLA` 1500/600HP/`PrismShot` 120 伤/射程 8/前置 `[RADAR,CACNST]` techLevel 6。
- **建议追加（本清单新提，未采纳）**：`SIDES` 里其它角色名同样会走这条静默通道，而它们**还能被写进 `buildOrder`/`vehicleMix`**：`heavyTank`（CA=`HOWI` 1900/800HP/前置 `[CAWEAP,CATECH]`，GA=`SREF`，NA=`APOC`）、`aaInf`（CA=`HOVI`，GA=`JUMPJET`，NA=`FLAKT`）、`radar`（GA 是数组 `['GAAIRC','AMRADR']`，CA 只有 `CARADR`）。建议给 `SIDES` 加一条启动自检：**对当前阵营逐角色断言 `av.has(R(role))`，不可造就 `log('warn')` 一次**（比 60 秒节流更好：开局一秒内就能看见）。

## #2（P0，已修 `97a1a42`）查打一体未实例化：`TAC is not defined` 每 3 秒吞掉该 tick 的攻城/修理/反击反射

**现象（时间 + 数据）**

- `tacticalMode: true`（v014 的卖点）从 **0:01** 起每约 3 秒一条 `[error] TAC is not defined`：0:01 / 0:04 / 0:07 / 0:18 / 0:21 / 0:24 / 0:27 / 0:30，**0:30 执行层自动把 `tacticalMode` 置 false** 并记 `今 查打一体内核未定义（TAC is not defined）：每 3 秒抛异常并跳过该 tick 的攻城/修理/反击反射。本局关闭，等内核接线修好后再启用`。
- 之后全程无 `tac[phase]`、无 `planned`、无 `lastVerify` 回执，`tacticalSuppressSec` 抑制窗口从未写入。

**影响**

- **本局"查打一体"按 0 动作计，请按"未验证"记录，不要写成"表现不好"。**
- **真损失是反射被跳过**：主循环顺序是
  `if (C.plan.tacticalMode && every('tactical', ...)) tacticalTick(C.state()); if (every('siege',0.7)) siege(...); if (every('repair',2)) repair(...); if (every('retaliate',2)) retaliate(...)`。
  异常从 `tacticalTick` 抛出时，后面三行**根本没被执行**，所以这三行的 `every()` 计时器**没有被消费**——它们只是**错过了这一 tick 的机会窗口，要等下一次自己的节流到期**。净效果：**每 3 秒一次异常，把 `siege`（0.7 秒节流，约每 4 次丢 1 次）、`repair`/`retaliate`（2 秒节流，约每 6 次丢 1 次）的执行频率各削掉约 25% / 17%。**
- 本局这个损失被掩盖了：`stance` 全程 `defend`（0 次转攻），所以 `siege` 无事可做；`repair` 只在 10:30 出现一条（`修理 CAREFN（血量 58%）`）说明它并非完全没跑。**不要据此认为这个 bug 无害**——match-013/014 那类"正在攻城时反射被吞"的形态会更贵。

**建议的代码改法（已采纳）**

- 补上 `const TAC = makeTacticalEngine({...})` 的实例化（两个坑：它原来被写在 `TACTICAL_CORE` 块内、被 `patch-tactical.py` 的幂等替换整块删掉；以及它引用了 `army()` 的局部函数 `towerRangeAt`，改为 `start()` 作用域内的实现）。
- 加静态接线自检 `scripts/tactical-runtime-wiring.test.js`（12 项，含"实例化恰好一次""在 core 块之外""每个依赖标识符都在它之前声明"的 TDZ 顺序检查，并做了反向验证）。**纯逻辑 22 项与接线 18 项在 match-017 全绿却仍然死链，原因是两套 suite 都自己用工厂造引擎、从不看 runtime.js 怎么接线**——这条值得写进所有后续"内联代码"的验收标准。
- **建议追加（本清单新提，未采纳）**：主循环里三个反射的调用**不应该被任何前置分支的异常连带**。最小改法是把 `tacticalTick` 那一行包进 `try { ... } catch (e) { log('error', 'tactical: ' + e.message); C.plan.tacticalMode = false; }`，并考虑把 `siege/repair/retaliate` 移到 `tacticalTick` 之前（这两条哪个都行，一起做更稳）。

## #3（未修，本局最大的失血源）自动转攻反射的判据里没有"目标基地成色"，只能用极端阈值以外科手术式关闭

**现象（时间 + 数据）**

| # | 时间 | 触发读数 | 出发 | 结果 |
|---|---|---|---|---|
| 1 | 2:19 | 我方 14 单位/6740 vs 敌方可见 2820（2.4 倍）、`field=0` 已 10 秒 | 14 单位 | 2:44 打剩 21% 自动撤退；**2:19–2:50 逐条重算 = 2640 : 5340 = 0.49:1** |

同一判据在 3:47（7590 vs 4500，1.69 倍）与 4:17（11010 vs 5700，1.93 倍）**两次正确挡下**——**本局它一共评估 4 次，2 挡 2 放，放行的两次都亏。挡下的那两次价值比反而更低**，说明"2 倍价值"这个门槛在"敌方龟缩"形态下与出门后能否拆掉目标几乎不相关。
两次的分母都是假的：敌方主力**全部停在离它出生点 15 格以内**（`atEnemyHome`），在 `field` 口径里显示 0；敌方基地当时**完整**（3 类生产建筑俱在、GAPILL 1:09 起就有、5:10 达 5 座）。对照 match-011（5:39 自动转攻成功）与 match-012（12:29 成功），那两次的敌方基地都已经被打软（家里只剩 3 JUMPJET+1 FV / 建造厂已被拆）。

**影响**

- 正面：**止住了本局最大的失血源**（两次转攻 16210，大于敌方唯一一次成建制总攻造成的损失——那次我方还是 2.07:1 有利）。
- 负面：**门槛抬高后我方 8:39 的 29 单位/19570 也"无反射可用"**，此后所有转攻决策都必须手动做（本局实际没做，指挥官按 T-043 核对 three 条件后选择不出门——那个判断是对的，但它是"人补机器的缺"）。
- 净评估：**在判据修好之前，这条反射的期望值是负的**（4 次实战：2 次灾难、1 次大亏、2 次成功且成功那两次敌方已被打崩）。保留 45 是止血，不是结论。

**推测原因**

`siege()` 的三个闸门是 `field` 为空 ≥`siegeQuietSeconds` + `hasVehicle` + 己方价值 ≥2× 敌方可见价值。**三个都不是"目标能不能拆"的判据**：
- `field` 语义在本平台（无战争迷雾）下会把"在家囤兵"读成"没有力量"；
- 价值比只比较**野战可见价值**，不含敌方静态防御、产能、以及 T-049 那种"射程差"；
- 没有任何一处读过"敌方可见 `isBaseDefense` 建筑数"或"敌方 `atEnemyHome` 的斜率"。

**建议的代码改法（条件型，不是数值型；**plan 层表达不了**，`DEFAULT_PLAN` 里没有对应键，写进 `candidate.json` 会被 `evolve.py` 的 unknown-field 校验拒绝）**

在 `siege()` 的自动转攻分支里加一道"敌基地成色"闸门，**任一不满足就不出门**：

1. **敌方可见静态防御数 == 0**（`S.hostile` 里 `isBaseDefense` 建筑；若从未侦察过敌方基地则视为未知 ⇒ 不出门）；
2. **敌方 `atEnemyHome` 价值不在上涨**（复用 `armyHist`，T-043）；
3. **我方在出发方向上具备射程覆盖手段**（有 `CTESLA`/`ATESLA`/`TESLA` 落地，或有 `isArtillery` 单位）——第 3 条是本局新增的，因为 T-049 的射程碾压会让"2 倍价值"完全失效。

**同时建议保留一个"人可强制"的出口**：把自动门槛拆成"自动"与"指挥官 `apply({stance:'attack'})`"两条路，自动那条受上面三闸门约束，手动那条不受（本局指挥官的手动判断是对的，不该被条件挡住）。
