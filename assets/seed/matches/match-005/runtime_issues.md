### A#1 资金饥饿保护 —— 细看

- **主目标达成**：这条反射的目的是让贵建筑收敛。ATESLA（1500）2:03 排产、2:37 落地；第 3 座 GAREFN（2000）2:02 排产、2:53 落地。都在 1 分钟内完成，对比 match-004 的 TESLA 3 分 23 秒只到 66%，**修复有效**。
- **抖动 22 次**：1:11、1:17、1:52、2:01、2:06、2:14、2:16、2:25、2:30、2:37、2:45 进入；1:16、1:28、1:59、2:01、2:13、2:14、2:24、2:29、2:34、2:44、2:51 退出。2:01 和 2:14 是同一秒进出——资金在 300 附近来回抖（矿车每卸一次矿资金跳到 300–800，下一 tick 被队列吃掉）。主会话已在 runtime.js 加滞回（<300 进、>800 出，`M.starved ? pd.credits < 800 : pd.credits < 300`），**本局未验证**，下局看 pause/resume 次数是否降到个位数。
- **对开局部队的副作用（任务书要求评估）**：结论是 **"暂停新排"本身没有少造任何一辆坦克，但"矿车豁免"让载具队列在关键窗口只造了一辆矿车**。证据链：
  1. 步兵：1:01 就到 `infantryCap 8`（8 E1），之后步兵队列本来就不排，保护对它无影响。
  2. 载具：1:53 排产第 5 辆 CMIN（`补矿车（4/6）`，矿车豁免不受保护影响）。资金恒 0，这辆 1400 的矿车到 2:51 才出来（**52 秒**）。同期队列里还有一辆 FV（2:37 取消时进度 0%），`vq.currentSize < 2` 已满，所以 **1:53–2:37 之间即使保护不存在也排不进第 3 辆灰熊**——队列被"矿车 + 0% 的 FV"占死了。
  3. 反过来说：如果矿车不豁免（或 `minersPerRefinery` 是 2），1:53 就不会排这辆矿车，载具队列的那 52 秒和 1400 会给 FV/MTNK。这正是 v005 把 `minersPerRefinery` 回到 2 的理由。
  4. 与 match-004 对比：match-004 2:41 时 16 单位 3880、5 矿车、3 矿厂、无 TESLA；本局 2:31 时 10 单位 2940、4 矿车、2 矿厂、ATESLA 65%。差的 940 ≈ ATESLA 已投入的 ~1000 —— **饥饿保护把钱按设计导向了塔**，不是它偷走了部队；是初始方案里塔 + 第 5 辆矿车 + 第 3 矿厂三项在 1:53–2:03 同时开工，而对手 2:32 就到。
- **建议改法**（`production()`）：矿车豁免加条件——`harvs < refs * 2`（每矿厂 2 辆是最低可用量）时才豁免；超过这个数的矿车和坦克一样受饥饿保护约束。这样 `minersPerRefinery: 3` 的"第 3 辆"只在有钱时排，不会在 0 资金下抢坦克窗口。

### 附：取消 FV 的退款核对
- 2:37 `方案已不需要，取消 FV（进度 0%，取消前资金 236）`。快照 2:31 资金 143、2:41 资金 0；期间 ATESLA 2:37 落地、GAPILL 2:47 排产、E1 在补。**10 秒粒度的快照无法证明退款**。但进度 0% 意味着这辆 FV 还没扣过一分钱（RA2 是按进度逐步扣款），预期退款本来就是 0，"资金 236 → 0"是被其他队列吃掉的，不是退款失败。

## B. 本局新发现的问题

### 1. 迎击点在防御塔射程外（影响：**高**，直接决定第 2 波的交换结果）
- **现象**：2:32 警报 `{"LTNK":2} @87,107，迎击点 83,110`。锚定塔是碉堡 (76,114)，迎击点离它 **8.0 格**（`leashRadius 8`），而 GAPILL 的 Vulcan2 射程 **5.5**；光棱塔 (78,119) 离迎击点 **10.3 格**，PrismShot 射程 **8**。8 E1 + 2 MTNK 被 AttackMove 到一个**没有任何塔火力覆盖**的点和 2 LTNK + 2 GHOST2 对射，2:35–2:44 全灭（交换 3620:3620）。match-004 也是同样的几何（迎击点离哨戒炮 5–8 格），只是那局 HTNK 对 HTNK 打得起。
- **推测原因**：`pt` 的半径只用 `P.leashRadius`，不看塔的武器射程；`anchorFor` 取的是"离威胁最近的塔"，不是"射程最长的塔"。
- **建议改法**（防守分支，`const pt = reach > P.leashRadius ? ...`）：
  1. 取每座塔的射程 `game.rules.getWeapon(tower.rules.primary).range`，迎击半径 = `Math.min(P.leashRadius, range - 1)`；
  2. 锚点优先选射程最长的塔（光棱塔 8 > 碉堡 5.5），让部队站在它射程内 1 格处；
  3. 方案层先用 `leashRadius: 4` 兜底（v005，T-021）。

### 2. 饥饿保护对矿车的豁免（影响：中；见 A#1 第 4 点）
- 建议改法已写在 A#1：`harvs < refs * 2` 才豁免。

### 3. 建筑队列在资金 0 时按 buildOrder 排 ≥800 的项（影响：中，T-013 的推广）
- **现象**：2:02 资金 565 排产第 3 座 GAREFN（2000）；2:53 资金 331 排产第 3 座 GAPOWR（800，余电 90 —— 电确实快不够，指挥官记录里的"400/85 富余"读错了）。前者和 ATESLA + 载具队列三方分零收入，让第 3 辆灰熊从未排上；后者到判负只有 17%。
- **推测原因**：`for (const role of P.buildOrder)` 只看 `counts` 和 `av.has`，不看资金（T-013 已指出，只对 factory 处理过）。
- **建议改法**（`production()` Structures 分支）：buildOrder 项若 `cost >= 1500` 且 `pd.credits < cost * 0.4`，跳过本轮（不删，下轮再看），并 `every('bo-wait', 30)` 记一条 `[reflex] buildOrder 的 X 等资金`；电厂在 `powerLeft < 100` 时不受此限制。

### 4. 光棱塔的放置位置（影响：中）
- **现象**：`placementCenter` 对 `isBaseDefense` 按已有塔数取 `side = (k % 3) - 1`：碉堡 #1 side −1 → (73,111)、碉堡 #2 side 0 → (76,114)、ATESLA 是第 3 座 → side +1 → (78,119)，落在防线南翼、紧挨 3 座矿厂 (75,116)/(78,120)/(79,117)，也是敌方进门后第一片目标区。3:20 被 2 LTNK + GHOST2 拆掉，只活了 42 秒。
- **建议改法**：`strongDef` 固定放 side 0（防线中央、正对来向），`baseDef` 放两翼；或者按"射程最长的塔放中央"排。另外矿厂 `0.6` 朝矿区的放置让三座矿厂全在来向一侧且互相相邻——GHOST2 C4 三秒拆三座。矿厂位置很难改，但至少 `strongDef` 应该盖住矿厂群的正面。

### 5. `trend` 在换群时误判（影响：中，情报质量）
- **现象**（analyst 逐条核对）：2:26 `lead`/`field` 都报 withdrawing，实际 armyTrack d57→54→48 在逼近，原因是前一刻 lead 是 d18 的单兵试探，被杀后换成 d57 的主力，距离差为正；2:55 同样（前一刻是撤退残兵 d10）；3:27 field 报 withdrawing，实际 4 辆增援在逼近，但和留在基地的 3 辆平均后中心变远。5 次采样 3 次错，距离数值本身全对。
- **建议改法**（`intelSample` / `C.intel`）：给 lead 记成员 id 集合，只有同一群（交集 ≥ 50%）连续 ≥3 次采样才输出 trend，否则输出 `trend: 'new'`；`field` 若含多个相距 >15 格的簇，不要给 trend。

### 6. `SIDES` 没有 CA（古巴）映射（影响：**潜在极高**，本局未触发）
- **现象**：`M.side = SIDES[M.sideKey] || SIDES.GA`。我方阵营随机，本平台至少有第三阵营 Confederation（建筑前缀 CA）。如果哪局我方抽到古巴，`sideKey === 'CA'` 会回落到 GA 表，所有角色解析成 GAPOWR/GAREFN/E1/MTNK……古巴一个都造不了，`M.unavail` 全部超时，执行层等于瘫痪。
- **建议改法**：补一张 CA 表（本局赛后从规则里核实，`unit_rules.json`）：`{power:'CAPOWR', refinery:'CAREFN', barracks:'CAHAND', factory:'CAWEAP', radar:'CARADR', tech:'CATECH', depot:'CADEPT', harv:'CHAR', baseDef: 待查（CA 的碉堡名未见）, strongDef:'ATESLA'（owner 含 Confederation）, tank:'LTNK', heavyTank:'HOWI', aaVehicle:'BGGY', inf:'PLA', aaInf: 待查, dog:'ADOG', engineer:'SENGINEER'}`。`baseDef` / `aaDef` / `aaInf` 需要下次抽到时用 `avail()` 看一眼。

### 7. `isArty` 正则把 HOWI 当炮兵（影响：潜在中，本局未触发）
- **现象**：清炮出击的 `isArty = /^(V3|ARTY|HOWI|DRED)$/`。本局赛后核实 **HOWI 是古巴的"中国天启"**（uiName APOCChina，1900，800HP heavy，武器 120mmxl + MammothTusk），不是炮兵。它 4:00 后大概率出现；`sortieMaxUnits 4` 会派 4 辆最快的载具（灰熊/FV）冲向一辆 800HP 的天启——正好是 match-003 "被引出去全灭"的翻版。
- **建议改法**：从正则里去掉 HOWI；改用 `o.rules.isArtillery || (weapon.range > 8 && weapon.minimumRange > 0)` 之类的规则判据，或者只用 rules 里的 `primary` 射程 ≥ 10 判断。

### 8. 指挥链时延对 30 秒间隔的连续压制无效（影响：结构性）
- analyst 每条 advise 比读到情报晚 10–18 秒（0:55→1:06、1:18→1:28、2:02→2:14、2:26→2:44、2:55→3:15）；指挥官一轮约 25 秒（3:30 读到崩盘、3:54 apply 落地时 3:49 已判负）。对古巴 29 秒一波的节奏，实时角色只能在 0:55–1:10 做一次性的阵营调整（T-020），之后全靠初始方案和反射。这不是 bug，但要写进角色任务书：**看到 CA 系建筑，当轮就 apply，不要等下一轮确认**。

### 9. 首见类型没有"步兵/载具"标注（影响：低，但本局误导了两个角色）
- **现象**：`首次发现敌方单位类型 GHOST2` 没有说明它是步兵。analyst 2:14 写"3 辆 GHOST2（应为载具/坦克）"，指挥官据此判断"第 2 波以载具为主"，其实 GHOST2 是 750 的海豹步兵（C4 拆楼）。
- **建议改法**（`intelSample`）：首见日志附 `o.isInfantry() ? '步兵' : o.isVehicle() ? '载具' : ''` 和 `cost`、`rules.armor`、主武器射程——三个字段就够角色判断克制关系。
