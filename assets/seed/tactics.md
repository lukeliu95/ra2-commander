每条战术都要能落到 plan 字段或指挥决策上，并附证据。

- 废弃条目保留不删，避免重复犯错。

- **数据口径提醒（match-009 复盘新增）**：`[kill]`/`[loss]` 事件消息里的 `{"HTNK":3}` 是**单条事件的战果**，跨窗口手工累加极易出错（match-009 两个实时角色独立地把一次 45 秒交战的交换比算成 2.8:1，逐条重算是 1.76:1）。引用交换比时**必须逐条重算并写明窗口起止**，且不要把"整局交换比"和"某一场交战的交换比"放在一起比较——档案里 match-004 的 1.13:1 是**整局**口径，match-009 的 1.76:1 是**2:56–3:41 单场**口径，两者不可直接比（match-009 整局口径见 T-017 证据）。
- **单位/建筑造价别再用旧值（match-015 复盘新增，务必照抄）**：本局从页面 `o.rules.cost` 实测——`E1 180 / ADOG 200 / FV 600 / MTNK 750 / JUMPJET 600 / CMIN 1400`（敌），`E2 **90** / DOG 200 / HTK **500** / HTNK 900 / HARV 1400`（我）。**`E2` 是 90 不是 180、`HTK` 是 500 不是 600**；用旧值逐条重算 match-015 的损失会得到 11720，而引擎 tally 是 10310（差 1410）。本局实测结果：击杀侧 54 个单位 25720 + 7 座建筑 11500 = **37220**（与引擎完全吻合），损失侧 23 个单位 = **10310**（同样吻合）。完整造价表与逐窗口重算见 `matches/match-015/intel_notes.md`。
- **实时 `tally` 的比值不要直接引用（match-015 补充）**：实时角色在同一段落里读到的 `tally` 是"截至那一刻"的快照，很容易出现"分子取 5:40、分母取 5:24"这类**跨时刻拼接**（match-015 分析员写的 38:1 就是这么来的，同刻正确值是 35:1），也有把单位造价用错的（本局 6:39 那条把 HTK×2+E2×3 算成 1650，实际 1270）。**归档一律以 `log.json` 逐条重算为准。**

### T-029 `defendRetreatRatio`（防守交战比例撤退）实战有效，但残部基数过小时会被单次多单位损失跳过阈值窗口

- 证据：**match-008（首次实战，支持+局限并存）**：

  - **局限**：3:20 交战中，我方从 3:16 的 1950（61.5% 换算基准，3:18 损失 1 MTNK 后剩 1200/61.5%，仍高于 40% 阈值不触发）到 3:20 同一 tick 内损失 2 FV（1200 价值）直接归零，比例从 61.5% 跳到 0%，从未落在 40% 的阈值窗口内——**反射在 0% 时才触发，此时部队已经打光，没有起到任何提前止损的作用**。根因不是阈值数值选错（无论设成 0.4 还是 0.5，只要两个单位在同一 tick 相关联阵亡且占比够大，都可能被跳过），而是"用相对交战起点的比例"这种判断方式，在残部基数已经很小（本局是 1350-1950）时粒度不够——一次相关联的多单位损失就能跨越整个阈值窗口。

### T-025（设计提案，未实战验证）交战时按装甲/兵种类型分兵种打，不要全军一个 AttackMove 点
- 规则：现在 `army()` 的交战分支（`threats.length` 分支）和进攻分支（`P.stance==='attack'`）都是把整个 `units`/`defenders` 组一次性 `AttackMove` 到同一个 `pt`/`A.target`，`siege()` 选建筑目标也只按 `siegeRank` 正则+距离排序，**完全没有按敌方单位的装甲类型分配我方兵种去打最克制的目标**。已有的 `warhead_verses` 克制表（见 `knowledge/units.json`）其实可以驱动更聪明的分兵：
  1. **反装甲优先**：我方载具（MTNK/LTNK 等 AP 弹头）应优先集火敌方重甲/中甲单位（heavy/medium armor，如 MTNK、HTNK、LTNK 自己），而不是被步兵/轻型单位吸引火力——AP 弹头对 flak/none 装甲只有 0.25，打步兵效率很差（match-005 数据：MTNK 105mm 打 GHOST2 只有 16/发）。
  2. **反步兵/防空交给专职单位**：SA/RifleBullet 弹头对 none/flak 装甲效率高（SA 对 none=1.0），我方步兵（E1）或专职单位应该去点杀敌方步兵和防空/侦察类轻单位，把坦克留给坦克打坦克。
  3. **优先点名高威胁支援单位**：像 match-006 的 SREF（疑似拆楼单位）、GHOST2 的 C4（一次拆建筑）这类"脆皮但输出极高"的支援单位，一旦识别出现（`enemyTypes`/`M.enemyTypes` 已经在记录首次出现时间），应该有专门的小队用 `Attack`（不是 AttackMove）点杀，而不是让它们混在大部队里被忽略、直到它们炸穿建筑。
  - **实现思路（供主会话评估）**：在 `army()` 的 `threats.length` 分支和 `attack` 分支里，把 `units`（或 `defenders`/攻城 `strikers`）按 `o.rules.primary` 的 warhead 类型分成 2–3 组（"重弹头组"打敌方 heavy/medium 目标、"轻弹头/步兵组"打敌方 none/flak 目标），每组各自选组内 `warhead_verses` 效率最高的敌方目标质心作为 `AttackMove`/`Attack` 目标，而不是共用一个 `pt`。`siege()` 里可以在 `enemyUnits.some(...)` 判断之外加一条：识别到 SREF/GHOST2 这类"建筑杀手"单位时，从 `armyUnits` 里分一小队用 `Attack`（对单位，不是对建筑）直接点名，优先级高于常规拆楼。
- 证据：无直接实战验证（本条是基于 `runtime.js` 代码审计 + `knowledge/units.json` 克制表的设计提案，不是从某局战报里直接得出的规律）。间接支持：match-006 的终局崩盘里 SREF/GHOST2 类单位（含苏军/古巴局的 GHOST2）多次证明了"专职拆楼单位混在大部队里不被优先处理"的风险——match-005 T-020 已经证明"针对性反制专门单位"有效（光棱塔专门克 GHOST2/LTNK），这条是把同样的思路从"防御塔选型"延伸到"部队分兵"。
- 置信度：支持 0 / 反对 0 → 候选（设计提案，待主会话实现后用 match-007+ 验证）

### T-032 拆敌方核电站（NANRCT）会引发核爆，必须**最后拆**并先把部队散开（match-009 新增机制）
- 规则：确认敌方有核电站（苏军 `NANRCT`；识别方式：`enemy.buildingsFirstSeen` 里出现，或 `knownBuildings` 含 `NANRCT`）后：
